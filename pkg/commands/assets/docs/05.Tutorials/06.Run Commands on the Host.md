# Run Commands on the Host

Otter containers share the host's home directory and display server
by default, but sometimes you need to run a command that lives on the
host itself — a host package manager, a GUI app, or a system tool.
Otter provides three ways to do this, each suited to a different
level of persistence.

## otter host-exec — one-off host commands

`otter host-exec` runs a single command on the real host from inside
the container. It uses the `host-spawn` helper under the hood.

```sh
otter enter my-box
```

Inside the container:

```sh
otter host-exec ls
otter host-exec podman ps -a
otter host-exec firefox
```

If invoked with no command, it drops into your host's login shell:

```sh
otter host-exec
```

### How host-spawn works

On official otter images, `host-spawn` is already installed at build
time — nothing extra is needed. On custom or third-party images,
`otter-init` (otter's container setup script) attempts to download
`host-spawn` automatically during the first container boot. If that
download fails (e.g. no network), `host-spawn` is installed on
demand the first time you run `otter host-exec`, with a confirmation
prompt in interactive shells. Pass `--yes` to auto-confirm:

```sh
otter host-exec --yes ls
```

`host-spawn` bridges the container's process into the host's context.
The host's `XDG_RUNTIME_DIR` and `DBUS_SESSION_BUS_ADDRESS` are
automatically remapped through `/run/host`, so GUI and D-Bus-dependent
commands (like opening a file manager or launching a browser) work
correctly.

### Automatic xdg-open and flatpak integration

During container initialization, otter sets up two convenience
symlinks inside every container — no configuration needed:

- **`xdg-open`** — if the container doesn't already have one (and
  there's no init system), otter symlinks it to `otter-host-exec`.
  Opening a URL or file from inside the container transparently opens
  it on the host.

  ```sh
  # Inside the container — opens on the host's browser
  xdg-open https://example.com
  ```

- **`flatpak`** — if the container doesn't already have flatpak
  installed, otter symlinks it to `otter-host-exec` so that any
  Flatpak desktop file's `Exec=` line (which references
  `/usr/bin/flatpak`) works transparently from the container.

## otter redirect — persistent host command aliases

`otter host-exec` works well for one-off commands, but typing
`otter host-exec <command>` every time gets tedious. `otter redirect`
creates a persistent wrapper binary inside the container's PATH that
transparently runs a given command on the host instead.

### Creating a redirect

```sh
# Make "podman" inside the container run host's podman
otter redirect add --host-cmd podman
```

Now just type `podman` inside the container and it runs on the host:

```sh
podman ps -a           # lists host containers
podman run --rm alpine # runs on the host
```

### Redirecting multi-word commands

When the host command is more than one word, `--as` is required to
give the redirect a name:

```sh
otter redirect add --host-cmd "rpm-ostree upgrade" --as rpm-up
```

Now `rpm-up` inside the container triggers `rpm-ostree upgrade` on
the host:

```sh
rpm-up
```

### Managing redirects

```sh
otter redirect list              # list all redirects in this container
otter redirect remove rpm-up     # remove a redirect
```

Redirects live at `/usr/local/bin/<name>` inside the container's own
filesystem. `add` refuses to shadow a real binary — it won't overwrite
existing tools. `remove` only deletes files it knows it created, so
it's safe to use without confirmation.

### Use cases

- **Host package managers**: redirect `dnf`, `apt`, `pacman`,
  `xbps-install` to run on the host without leaving the container.
- **Immutable distros**: redirect `rpm-ostree` or `bootc` commands.
- **Flatpak management**: `flatpak install` on the host while working
  inside the container.
- **System tools**: `systemctl --user`, `journalctl`, `nmcli`, or
  any host-side CLI you use regularly.

## Using host Docker/Podman from inside the container

If your host runs Docker or Podman and you want to control it from
inside an otter container, create a redirect for it:

```sh
# Inside the container
otter redirect add --host-cmd podman
otter redirect add --host-cmd docker
```

Now both `podman` and `docker` inside the container control the
host's instances directly:

```sh
podman ps -a
docker build -t my-app .
```

## Copying text to the host clipboard

To copy text from inside the container to the host clipboard, install
the appropriate clipboard tool inside the container:

```sh
# For X11 hosts
sudo apt install xsel    # Debian/Ubuntu
sudo dnf install xsel    # Fedora
sudo pacman -S xsel      # Arch

# For Wayland hosts
sudo apt install wl-clipboard    # Debian/Ubuntu
sudo dnf install wl-clipboard    # Fedora
sudo pacman -S wl-clipboard      # Arch
```

Then use it normally — since otter shares the host's display server
sockets, clipboard tools work across the container boundary:

```sh
# X11
echo "hello" | xsel --clipboard
xsel --clipboard --output

# Wayland
echo "hello" | wl-copy
wl-paste
```

## Notes

- On official otter images, `host-spawn` is already present — no
  download needed. On custom images, `otter-init` attempts to fetch
  it during first boot; if that fails, it's installed on demand when
  you first run `otter host-exec`.
- `host-exec` must be run inside a container — it checks for
  `/run/.containerenv`, `/.dockerenv`, or a `container` environment
  variable and refuses to run on the bare host.
- Redirects are per-container. Each container maintains its own set
  independently.
- `xdg-open` and `flatpak` symlinks are set up during `otter-init`
  (first container boot), not on each `host-exec` call.
