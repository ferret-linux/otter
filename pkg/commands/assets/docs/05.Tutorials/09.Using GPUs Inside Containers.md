# Using GPUs Inside Containers

GPUs inside otter containers work in one of two ways: either the
container uses its own vendor-provided compute stacks (ROCm, oneAPI,
Mesa), or it reaches into the host's already-configured GPU setup
(NVIDIA). Which path applies to you depends entirely on which GPU you
have.

## Understanding the kernel constraint

The container's kernel is the **host's kernel** — the exact same
kernel the host boots, just seen from a different userspace. This
means:

- The kernel version inside the container is always the host's.
- You **cannot install kernel modules (KMs) inside the container**.
- You cannot install host-only extras (kernel headers, DKMS packages,
  `akmod`, etc.) and expect them to load — there is no kernel to build
  against that isn't the host's.

Anything that needs kernel-level support must already be provided by
the host kernel. The container can only carry *userspace* pieces:
libraries, toolkits, compilers, and OSS driver stacks that talk to the
shared kernel drivers.

This single constraint is why GPU support looks completely different
for NVIDIA vs. AMD/Intel, and why vendor modules that are built in to
the kernel (AMD's `amdgpu`, Intel's `i915`) need no extra handling
while NVIDIA's out-of-tree driver does.

## NVIDIA

### Host requirements

NVIDIA GPUs have a hard requirement: the **NVIDIA proprietary drivers
must be installed and working on the host**. Otter cannot install them
for you, and they can't exist "inside" the container since they
require the out-of-tree `nvidia` kernel module. The container will
reach into the host's driver setup, so if the host drivers are broken
or missing, nothing inside the container can help.

With the driver in place, you have two ways to give the container GPU
access, selected at creation time with `--gpu`:

### --gpu=nvidia (best-effort, battle-tested)

```sh
otter create --image fedora my-box --gpu=nvidia
```

This mode integrates the host's NVIDIA drivers into the container: it
bind-mounts the host's driver libraries and devices, so the container
can use the GPU immediately. It's the quickest path and — while
described as "best-effort" — it's heavily tested and works reliably in
practice.

Compute works as long as the container has the **matching CUDA
runtime** installed for the host driver version. In general the rule
is: install a CUDA version that is *compatible with* (not necessarily
identical to) the host driver version. NVIDIA maintains a
compatibility list between driver versions and CUDA toolkits; a CUDA
toolkit that requires a specific minimum driver version works as long
as the host driver is at least that version.

Inside the container:

```sh
# Example — install a CUDA toolkit compatible with your host driver
# (method depends on the container's distro, e.g. NVIDIA's apt/yum repos)
```

Then verify the container sees the GPU:

```sh
nvidia-smi
```

If `nvidia-smi` works inside the container, the integration is good.

### --gpu=nvidia-toolkit (official, most robust)

```sh
otter create --image fedora my-box --gpu=nvidia-toolkit
```

This mode delegates entirely to NVIDIA's own
**nvidia-container-toolkit**: the host's `nvidia-ctk` injects the GPU
at container-create time via CDI, following the toolkit's officially
supported, tested path. It's the recommended and most robust way to
use an NVIDIA GPU with otter when the toolkit is available on the
host.

Requires nvidia-container-toolkit installed and configured on the
host (with rootful setup done via `nvidia-ctk` as needed).

### Which mode should I use?

| Situation                                     | Recommendation                      |
| --------------------------------------------- | -------------------                 |
| nvidia-container-toolkit installed on host    | `--gpu=nvidia-toolkit`              |
| No toolkit, but NVIDIA driver is on the host  | `--gpu=nvidia`                      |
| Heavily-tested, stable workloads              | either — both work reliably         |
| Vulkan / non-CUDA GPU workloads               | `--gpu=nvidia` typically sufficient |

## AMD & Intel

AMD and Intel GPUs don't need special handling. The host kernel has
**built-in drivers** (`amdgpu`, `i915`) for these GPUs, so there is no
out-of-tree kernel module problem like there is with NVIDIA — nothing
extra is required on the host, and the container doesn't need to
reach into host drivers.

GPUs just work out of the box with the default `--gpu=mesa`:

```sh
otter create --image fedora my-box     # --gpu=mesa is the default
```

Inside the container, the Mesa OSS userspace drivers (from the
container's own packages) drive the GPU through the shared kernel
drivers. Verify with:

```sh
glxinfo | grep "OpenGL renderer"
vulkaninfo --summary
```

## ROCm & oneAPI

AMD's ROCm and Intel's oneAPI are *userspace-only* compute stacks —
they don't need kernel modules. That means you can **install them
directly inside the container**, like any other package, no special
`--gpu` handling needed.

```sh
otter enter my-box
# Inside the container — install ROCm or oneAPI with the container's
# native package manager, then use it as usual
```

Since the container shares the kernel's `amdgpu`/`i915` drivers, the
compute stack talks to the GPU through them exactly as it would on the
host. Just make sure the container has the userspace pieces the
compute stack needs (e.g. Mesa/libdrm via its packages).

## CUDA: two paths

For CUDA workloads you have two options:

1. **`--gpu=nvidia`** — pair it with a CUDA toolkit installed *inside
   the container* that is compatible with the host driver version
   (see the compatibility table for your driver). The container
   doesn't get CUDA from the host — it brings its own, matched to the
   host driver.

2. **`--gpu=nvidia-toolkit`** — if the *host* already has a CUDA
   install, the toolkit hands the container access to it directly.
   No need to install CUDA inside the container at all.

Choose based on whether you want CUDA inside the container (option 1)
or shared from the host (option 2).

## Troubleshooting

- **`nvidia-smi` not found**: install it in the container, or use
  `--gpu=nvidia-toolkit` to share the host's.
- **`nvidia-smi` errors / no devices**: the host driver isn't
  installed or working — check `nvidia-smi` **on the host** first.
- **CUDA application can't find a device**: the CUDA toolkit inside
  the container may be too new for the host driver. Install a CUDA
  version compatible with your driver version.
- **AMD/Intel GPU missing**: verify with `lspci | grep VGA` on the
  host — if the host kernel sees it, the container should too.
- **Kernel module errors**: remember you can't install KMs in the
  container. Anything needing one must come from the host.

## Notes

- All `--gpu` values can also be set in a manifest via
  `hardware.gpu` when using `otter assemble`.
- The container shares the host kernel — kernel modules can never be
  installed inside it.
- For NVIDIA, the host driver being installed is a hard requirement
  in every mode.
