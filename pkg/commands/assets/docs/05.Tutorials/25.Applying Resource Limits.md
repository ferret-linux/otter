# Applying Resource Limits

Otter supports limiting how much CPU and memory a container can
use. Limits can be set at creation time (permanent) or applied to
a running container via systemd (transient). This tutorial covers
both approaches.

## Setting limits at creation time

Use `--memory` and `--cpu-threads` on `otter create`:

```sh
otter create --image fedora --memory 2G --cpu-threads 2 dev-box
```

- `--memory` accepts values like `512m`, `2G`, `4g` — any format
  the container manager's `--memory` flag accepts.
- `--cpu-threads` sets the maximum number of CPU threads the
  container can use.

These limits are stored as part of the container's configuration
and persist across restarts. To verify, use `otter inspect`:

```sh
otter inspect dev-box
```

The output shows `Memory: 2G` and `CPU Threads: 2 threads` in the
resource limits section.

## Declarative limits in manifests

If you use `otter assemble`, set limits in the `hardware` section:

```toml
[[container]]
name  = "dev-box"
image = "fedora"

hardware.memory = "2G"
hardware.cpu    = 2
```

These map directly to `--memory` and `--cpu-threads` on the CLI.
Limits set this way are recreated every time you run
`otter assemble create`.

## Applying limits to running containers

For containers that are already running, you can modify resource
limits on the fly using systemd's resource control. This requires
rootless podman or docker with cgroups v2.

First, find the container's full ID:

```sh
podman ps --all --no-trunc --format "{{.ID}} {{.Names}}" | grep dev-box
```

Or use `otter inspect`:

```sh
otter inspect dev-box --json | jq -r '.id'
```

Then apply limits with `systemctl --user set-property`:

```sh
# Limit to 2G of memory
systemctl --user set-property libpod-<container-id>.scope \
  MemoryMax=2G

# Limit to 20% of a single CPU
systemctl --user set-property libpod-<container-id>.scope \
  CPUQuota=20%

# Pin to specific CPU cores
systemctl --user set-property libpod-<container-id>.scope \
  AllowedCPUs=0,1

# Adjust IO weight (1-10000, higher = more bandwidth)
systemctl --user set-property libpod-<container-id>.scope \
  IOWeight=500
```

Run `man systemd.resource-control` for the full list of properties.

## Transient vs persistent

Limits applied via `systemctl --user set-property` are
**transient** — they're lost when the container is stopped and
restarted. To make them persistent across restarts, move the
drop-in file:

```sh
# Check where the drop-in lives
systemctl --user status libpod-<container-id>.scope

# Move it to a persistent location
mkdir -p ~/.config/systemd/user/libpod-<container-id>.scope.d
cp /run/user/$(id -u)/systemd/transient/libpod-<container-id>.scope.d/50-MemoryMax.conf \
   ~/.config/systemd/user/libpod-<container-id>.scope.d/

systemctl --user daemon-reload
```

Limits set via `otter create --memory`/`--cpu-threads` or
manifests are persistent by design — they're applied every time
the container is created.

## Checking current limits

```sh
otter inspect dev-box
```

Shows memory and CPU threads in the output. For detailed systemd
resource stats on a running container:

```sh
systemctl --user status libpod-<container-id>.scope
```
