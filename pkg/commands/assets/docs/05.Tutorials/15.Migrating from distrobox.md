# Migrating from distrobox

Otter shares a lot of ideas (and some code) with distrobox, so moving
is fairly mechanical. There is **no** `otter migrate` command, and
there are no plans to add one. Migration is a manual process — you
either recreate your containers fresh or reuse a distrobox container
as the image for a new otter container. If you just want a clean
start, creating a new container with `otter create` is always the
simplest path:

```sh
otter create --image debian my-new-box
```

The rest of this guide covers the by-image migration path and the
backend-specific notes.

## Migrate an existing container (podman / docker)

If you have an existing distrobox container you'd rather keep than
rebuild, you can turn it into an image and feed that image to a new
otter container. There are three steps:

**1. Commit (save) the running distrobox container to an image:**

```sh
# list your distrobox containers
distrobox list

# save one to a local image (podman backend shown)
podman commit my-distrobox my-distrobox-image:latest

# docker backend
docker commit my-distrobox my-distrobox-image:latest
```

**2. Remove the distrobox container** once you no longer need it:

```sh
distrobox rm my-distrobox
```

**3. Create a new otter container from the committed image:**

```sh
otter create --image my-distrobox-image:latest new-box
```

Any full image reference (something containing `/` or `:`) is used
as-is, so the committed image is picked up straight from your local
image store. See `Using Custom Images` for how image resolution works.

### Caveats of reusing a distrobox image

This approach treats your old container as a foreign image, which
comes with a few caveats:

- **No registry support.** The committed image lives only in your
  local image store; it is not published to any registry.
- **Treated as a non-official image.** Otter will flag it as a
  third-party/non-official image, and your experience may vary since
  it lacks otter's pre-configured setup.
- **Slower one-time setup.** Because it isn't an otter-blessed image,
  start/enter do extra setup, so first boot is noticeably slower than
  with a native otter image.
- **distrobox-specific state is not migrated.** Exports and other
  distrobox-managed extras do not carry over; you'll need to recreate
  them in otter (see `Exporting Apps & Binaries`).

If you don't need to preserve container state, prefer creating a
native container from an official otter image instead — it avoids all
of the above.

## lilipod / podman-launcher users

Neither `lilipod` nor `podman-launcher` has native support in otter.
The practical options depend on which one you use:

- **podman-launcher** — follow the podman flow above: commit using
  `podman-launcher` and do the rest with `podman`. Alternatively, you
  can symlink `podman-launcher` to `podman` and use it; this *may*
  work but is not guaranteed. Either way the steps are the same as the
  podman guide: commit, remove, then create.
- **lilipod** — there is no support, because lilipod has no `commit`
  or save option. You cannot turn a lilipod container into an image,
  so just recreate your container from scratch with `otter create`.

## Manifest / assemble users

If you manage distrobox containers declaratively, note that distrobox
uses `.ini` manifest files while otter uses `.toml` files. There is no
automatic migration and no backwards compatibility between the two
formats. You are expected to translate your containers yourself using
the `Manifests` documentation and the example manifests shipped under
`/extras` (`extras/manifest.toml` and
`extras/manifest-example.toml`).

Since the container model and most flags map closely between distrobox
and otter, translating a manifest is usually a line-by-line rewrite
rather than a redesign.
