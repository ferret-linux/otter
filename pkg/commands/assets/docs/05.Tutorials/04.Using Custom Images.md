# Using Custom Images

Otter's built-in registry images (ghcr.io/ferret-linux/*) come
pre-configured with shells, sudo, locale, timezone, and otter's
directory layout already in place. But you're not limited to them —
otter works with any OCI-compliant image. This tutorial covers three
ways to bring your own image: pulling from a remote registry, using a
locally built image, and building from a Containerfile.

## How image resolution works

When you pass `--image` to `otter create`, otter decides how to
handle it based on what it looks like:

- **Short name** (e.g. `fedora`, `alpine`) — resolved against
  otter's built-in registry catalog. These always point to official
  otter images.
- **Full reference** (anything containing `/` or `:`) — used exactly
  as given, bypassing the registry entirely. This is how you use
  custom images.

```sh
# Short name — resolves to ghcr.io/ferret-linux/fedora-otr:stable
otter create --image fedora my-box

# Full reference — used as-is, no registry lookup
otter create --image docker.io/library/debian:bookworm my-box
```

If the image isn't already present locally, otter pulls it
automatically before creating the container.

## 1. Using an image from a remote registry

Any image hosted on Docker Hub, GHCR, Quay, or any other OCI
registry can be used directly by its full reference. Just pass the
full image path to `--image`.

### Docker Hub

```sh
otter create --image docker.io/library/ubuntu:24.04 my-ubuntu
otter create --image docker.io/alpine:edge my-alpine
```

### GitHub Container Registry

```sh
otter create --image ghcr.io/void-linux/void-glibc-full:latest my-void
```

### Quay.io

```sh
otter create --image quay.io/fedora/fedora:44 my-fedora
```

### Short names on Docker Hub

For Docker Hub's official images and library images, you can often
omit the `docker.io/` prefix — the container manager fills it in:

```sh
otter create --image debian:bookworm my-debian
```

### Pulling manually first

If you prefer to pull the image yourself before creating a container
(e.g. to inspect it or because you're working offline afterward):

```sh
# Pull with your container manager directly
podman pull docker.io/library/debian:bookworm
# or
docker pull docker.io/library/debian:bookworm

# Then create — otter finds the already-pulled image locally
otter create --image docker.io/library/debian:bookworm my-debian
```

### Always pull fresh

Add `--always-pull` to force otter to re-pull the image even if it
already exists locally:

```sh
otter create --image docker.io/library/debian:bookworm --always-pull my-debian
```

## 2. Using a locally built image

If you've built an image on your host (with `podman build`, `docker
build`, or similar), it lives in your local image store. Reference it
by its name and tag:

### By name and tag

```sh
# Build an image locally
podman build -t my-custom-image:latest .

# Use it with otter
otter create --image my-custom-image:latest my-box
```

### By image ID

You can also use the image's ID (truncated is fine):

```sh
podman images
# REPOSITORY          TAG       IMAGE ID
# my-custom-image     latest    a1b2c3d4e5f6

otter create --image a1b2c3d4e5f6 my-box
```

### Export/import workflow

If you have an image tarball from another machine or a CI pipeline:

```sh
# Import the tarball into your local image store
podman load < my-image.tar.gz
# or
docker load < my-image.tar.gz

# Then create the container
otter create --image my-image:latest my-box
```

## 3. Building from a Containerfile

You can write a Containerfile tailored for otter and build it before
creation. This is the most powerful approach — you control exactly
what goes into the image.

### Minimal example

Create a `Containerfile`:

```dockerfile
FROM docker.io/library/debian:bookworm

RUN apt-get update && apt-get install -y \
    bash-completion \
    curl \
    git \
    vim \
    && rm -rf /var/lib/apt/lists/*

RUN useradd -m -s /bin/bash myuser
```

Build it:

```sh
podman build -t my-otter-custom:latest .
# or
docker build -t my-otter-custom:latest .
```

Create a container from it:

```sh
otter create --image my-otter-custom:latest my-custom-box
```

### Adding otter-friendly extras

Otter expects certain things to exist inside a container for the best
experience. While otter's init process (`otter-init`) handles most
setup automatically on first boot, you can speed things up by
pre-installing some basics in your image:

```dockerfile
FROM docker.io/library/fedora:44

# Pre-install common tools and a supported shell
RUN dnf install -y \
    bash-completion \
    curl \
    git \
    sudo \
    vim \
    && dnf clean all

# A supported shell (bash, zsh, fish, nu)
RUN dnf install -y zsh && dnf clean all
```

This avoids the one-time setup delay on first `otter enter` and
avoids the warning about non-official images if the Containerfile
produces an image derived from the upstream otter image.

### Using --additional-packages alongside a custom image

You don't have to bake everything into the image. Otter can install
additional packages during container creation:

```sh
otter create --image my-custom-image:latest \
  --additional-packages "tmux htop neovim" \
  my-box
```

This runs the image's native package manager to install the listed
packages on top of whatever's already in the image.

## Caveats with custom images

- **Slower first enter**: otter's init process has to detect the
  distro, set up shells, configure sudo, and lay out its directory
  structure on first boot. Official otter images already have all of
  this baked in, so custom images take noticeably longer on the first
  `otter enter`.

- **Shell fallback**: if you request a shell (via `--shell` or
  `settings.shell`) that isn't available in the image and can't be
  installed via the package manager, otter falls back to `bash`. If
  `bash` isn't present either, you'll land in `/bin/sh`.

- **Unsupported distro quirks**: otter tries to adapt to any OCI
  image, but some distros have package names, paths, or behaviors
  that differ from what otter expects. Official otter images have
  these quirks fixed at build time; custom images may not.

- **No staleness tracking**: otter's registry staleness tracking
  only applies to official otter images. Custom images are pulled
  once and then left alone unless you pass `--always-pull`.
