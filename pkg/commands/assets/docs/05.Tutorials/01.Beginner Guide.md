# Beginner Guide

A guided walkthrough of everyday otter usage: creating your first
container, managing its lifecycle, keeping it up to date, removing it
cleanly, working with rootful containers, and a few other basics
you'll reach for often. If you just want the fastest path to a
running container, see getting-started.md
instead — this guide covers the same ground in more depth, plus more.

## 1. Creating your first container

A container is created with `otter create` (or its shorter alias,
`otter mk`):

```sh
otter create --image fedora my-fedora-box
```

`--image` picks the base image — here, `fedora`, a short name resolved
against otter's built-in registry (see registry.md & images.md).
You can also pass a fully-qualified image reference instead
(anything containing `/` or `:`), which bypasses the registry and is
used as-is. The last argument is the container's name.

Both are actually optional. Leave out `--image` and otter uses your
configured default image; leave out the name and otter derives one
from the image (`fedora` becomes `my-fedora`), or falls back to
`my-container` if `--image` was also omitted. See
otter-create for the full set of creation
options — custom home directories, memory/CPU limits, an init system,
GPU integration, and more.

`create` pulls the image if it isn't already present locally, then
builds a container that's integrated with your host by default: your
home directory, `/dev`/`/sys`, and network namespace are all shared
with the container out of the box, so it feels like a native part of
your system rather than an isolated sandbox. Running `create` again
with the same name is safe — it won't recreate or modify an existing
container, it just tells you how to enter it.

Once created, drop into it with:

```sh
otter enter my-fedora-box
```

This starts the container if needed, waits for its setup to finish,
and gives you an interactive shell as your own user, with your own
home directory and most of your host environment variables carried
in. You can also run a single command instead of a full shell:

You may think why `otter start` exists if `otter enter` will auto
start the container by itself if needed. This is a good query & let
me explain the reason why `start/up` exists

If you want to startup multiple containers at once or in a series
or want to setup a service that auto-starts containers for you on
boot, then `otter start` is a much better choice then `otter enter`
as it attaches itself to a pty/tty by default

```sh
otter enter my-fedora-box -- cat /etc/os-release
```

anything after `--` on the `enter/sh` command is treated as a cmd
to run inside the container shell, in this case it will show the
output of command `cat /etc/os-release`

## 2. Managing its lifetime

Once you have more than one container around, `otter list` (or
`otter ls`) is the quickest way to see what exists and what state
it's in:

```sh
otter list
```

`otter list` or its alias `otter ls` will show all the created containers
(You will have to append `--root` if you are making rootful containers)

From there, the usual lifecycle commands apply:

```sh
otter stop my-fedora-box     # stop it
otter start my-fedora-box    # start it again
otter restart my-fedora-box  # stop + start in one step
otter pause my-fedora-box    # freeze it in memory without stopping it
```

A couple of things worth knowing:

- `restart` isn't a separate operation under the hood — it's just
  `stop` followed by `start`, which is why it works fine even on an
  already-stopped container. It exists just as a convenience tool.
- `pause` freezes every process inside the container in place (useful
  for reclaiming CPU temporarily) without actually stopping it, so
  resuming is instant. It only affects containers that are currently
  running.

All of these accept multiple names at once (comma-separated), or
`--all` to target every container you have.

For a closer look at one specific container than `list`'s one-line
summary gives you, `otter inspect` (or `otter info`) shows its full
configuration — resource limits, enabled features, namespace
isolation settings, and more:

```sh
otter inspect my-fedora-box
```

## 3. Upgrading & staying in sync

There are three different things that can be "out of date," and otter
handles them separately:

**Packages inside the container** — upgraded with:

```sh
otter upgrade my-fedora-box
```

This runs the container's native package manager upgrade routine
(`apt`, `dnf`, `pacman`, and so on, depending on the distro) inside
the container, starting it first if it isn't already running.

**The base image itself** — tracked separately by the registry. Every
official otter image carries a build number, and otter compares your
local image against the latest known upstream build whenever it's
relevant (e.g. on `create`, or when you run `otter registry list`).
Depending on how far behind you are, otter either warns you or pulls
the newer image automatically. This is a different kind of "staying
in sync" than `upgrade` — one keeps packages current *inside* an
existing container, the other keeps the *image* you'd create new
containers from current. See registry.md for
the full picture.

**The inside container scripts** — scripts or commands such as `otter-init`
that exist only inside the container — can occasionally become outdated or
fall out of sync with the version of Otter currently installed on the host.
To keep them synchronized, `otter upgrade` handles them automatically.
After upgrading, simply restart the container or reload the container's
shell, and the scripts will be synchronized with the current version of
Otter.

## 4. Removing a container

```sh
otter remove my-fedora-box
```

This deletes the container itself, along with anything otter created
on the host on its behalf: binaries previously exported with
`otter-export --bin`, desktop application entries exported with
`otter-export --app` (and their icons), and the container's own
generated desktop entry. Add `--rm-home` if you also want its home
directory deleted — otherwise your home directory contents are left
untouched on the host. `remove` also accepts `--all` and
comma-separated names, same as the other lifecycle commands.

If a container is locked (see below), `remove` skips it unless you
pass `--bypass-lock`.
`--bypass-lock` exists as a last-resort option for force-removing a locked
container that can no longer be safely unlocked due to a broken, crashed, or
otherwise unreachable state. It deliberately ignores and overrides the
container's locked status, bypassing the protections provided by `otter lock`.
This should only be used when the container cannot be recovered or unlocked
normally and removal is the intended final action.

## 5. Rootful containers

Every command so far defaults to rootless containers. Passing
`--root` (or `-r`) to `create`, or to any of the lifecycle/management
commands above, switches to a rootful container instead:

```sh
otter create --image fedora my-root-box --root
otter enter my-root-box --root
otter list --root
```

Rootless and rootful containers are tracked entirely separately —
`otter list` only shows one or the other depending on whether
`--root` is passed, so a rootful container won't show up until you
ask for it explicitly. `--root` is the preferred way to get a rootful
container; avoid `sudo otter create`, which runs otter itself as root
rather than just the container.

## 6. A few other basics

**Locking a container** protects it from accidental removal or
upgrades:

```sh
otter lock my-fedora-box
otter unlock my-fedora-box
```

A locked container is skipped by both `otter remove` and
`otter upgrade` until it's unlocked (or `remove` is forced past the
lock with `--bypass-lock`).

**Checking a container's health** from the inside, once you're in it:

```sh
otter enter my-fedora-box
otter doctor
```

`doctor` runs a fixed set of read-only checks (container detection,
network reachability, init-system status, and more) and reports
`[OK]`/`[WARN]`/`[FAIL]` for each — useful as a first step when
something feels off, before digging further by hand.
