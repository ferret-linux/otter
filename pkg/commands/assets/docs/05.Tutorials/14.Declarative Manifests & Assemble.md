# Declarative Manifests & Assemble

Manifests let you describe one or more containers declaratively in a
single TOML file, then create or remove them all with one
`otter assemble` command. They make a fixed dev environment
reproducible, and are the easiest way to set up a fresh machine with
several containers preconfigured.

This tutorial walks through a full example. For the complete field
reference and merge rules, see `Manifests`.

## Writing a manifest

Each container in the file is a `[[container]]` entry. A minimal one
only needs a name and an image:

```toml
[[container]]
name  = "dev"
image = "debian"
```

You can declare as many as you like. Fields like `image`, packages,
and exports mirror the corresponding `otter create` flags:

```toml
[[container]]
name          = "dev"
image         = "fedora"
start-now     = true
force-pull    = true

[settings]
shell       = "fish"
init-system = true
lock        = true

[additional]
packages = ["git", "vim", "tmux"]
volumes  = ["/tmp/test:/run/a"]

[hardware]
memory = "2g"

[exported]
apps = ["htop"]

[[container]]
name    = "dev-based"
include = "dev"
# inherits everything from "dev" except the fields you override here
```

Notes on this example:

- `[settings]` maps to shell choice, init system, rootful mode,
  desktop entry generation, and whether the container is locked after
  setup — see `Manifests` for every field.
- `[additional]` mirrors `--volume`, `--additional-flags`, and
  `--additional-packages`.
- `[hardware]` maps to `--memory`, `--gpu`, and `--cpu-threads`.
- `include = "dev"` inherits all fields from another entry in the
  same file; the including entry's own explicit values win.

## Creating the containers

```sh
otter assemble create --file my-setup.toml
```

This provisions every container in the file — pulling the image,
running setup, and applying the hooks/exports/locking each entry asks
for — in one batch. As with `otter create`, a partial failure rolls
back the just-created container instead of leaving it half-set-up.

Use `--replace` (`-R`) to delete an existing container with a matching
name first, and recreate it from the manifest:

```sh
otter assemble create --replace --file my-setup.toml
```

## Removing the containers

```sh
otter assemble remove --file my-setup.toml
```

Removes every container the manifest declares. To target just one
entry, give its name:

```sh
otter assemble remove my-dev --file my-setup.toml
```

## Locking containers

`otter lock` marks a container so `otter remove` and `otter upgrade`
skip it, writing a lock file to `/usr/lib/otter/container.lock`
inside the container. The container must be running to lock it. In a
manifest you can ask for this automatically with
`settings.lock = true`. To force removal of a locked container, pass
`--bypass-lock` to `otter remove`. See `otter lock` and
`otter unlock` for the imperative forms.

## Cloning an existing container

If you want a new container that starts from the current state of an
existing one — for renaming it, or branching off multiple copies of
the same environment — use `otter create --clone`:

```sh
otter create --clone my-box my-box-copy
```

The source container must be stopped first; it is committed to a
dated image tag (`<name>:<YYYY-MM-DD>`) that becomes the new
container's image. These clone images are not tracked by otter's
registry. The manifest equivalent is the `clone` field: set
`clone = "my-box"` instead of `image` on a `[[container]]` entry.
