# InitSystems Inside Containers

Most otter containers don't need an init system — `otter enter` and
`otter host-exec` work perfectly well without one. But when you want
to run background services, manage daemons, or have a container that
behaves like a self-contained machine, `--init` gives you a real init
system inside the container.

## What --init does

```sh
otter create --image fedora my-box --init
```

`--init` (short `-I`) launches an init system inside the container as
PID 1. This is useful when you want an **independent init system
inside the container** — for services, sshd, scheduled jobs, and so
on.

It has nothing to do with `--init-hooks` or `--pre-init-hooks`
(which run setup commands), `init` here stands for *init system*.

### What it unshares

`--init` implies two namespace flags:

- **`--unshare-process`** — the container gets its own PID namespace,
  so host processes are invisible from inside it (and it can't see or
  signal them).
- **`--unshare-groups`** — the container's secondary host groups are
  not forwarded; entry uses `su` for a proper login shell instead.

This is what makes a real init system safe to run: with host
processes out of sight and its own PID 1, the init system can manage
the container's services cleanly.

## Which init systems are supported

Otter detects the init system available inside the image (at setup
time) in this order:

1. `systemd`
2. `openrc`
3. `sysvinit` (`telinit` present — LSB or BSD layout)
4. `runit`
5. `dinit`
6. `generic` (any other `/sbin/init`)

### systemd — first-class, most battle-tested

systemd gets the most testing and is **the** recommended init system
for containers. It's the most reliable and most heavily verified
option — every otter feature that touches init systems (user
sessions, socket integration, lingering) is tested against systemd
first. Most official otter images ship systemd out of the box, so:

```sh
otter create --init --image fedora my-box
```

usually needs no extra packages at all.

### sysvinit, runit, dinit, openrc — first-class, verified but newer

These four have the same first-class integration as systemd — full
setup, console handling, and user-session integration — but haven't
received the same years of battle-testing yet. They've been verified
and tested to work, and for everyday service management they're
solid.

Depending on the base image you may need to add the init system
packages yourself, but official images include them by default:

```sh
otter create --init --image alpine
otter create --init --image arch
otter create --init --image devuan
```

### busybox, toybox, and everything else — generic support

Any init not in the five above — busybox init, toybox init, and
similar — falls back to **generic** support: otter launches `/sbin/init`
as PID 1 and considers the container ready. Generic inits get the
basic enabling treated to work, but nothing more: no readiness wait,
no structured status concept, and no service-management integration.
`otter service` won't dispatch for them, and `otter doctor` reports
them without a real health check.

They work fine for simple inits, just with less otter integration.

## Init systems are independent of the host

An important property: **the init system inside the container doesn't
need to match the host's.** Otter doesn't care what your host boots.

This means you can run systemd in one container, OpenRC in another,
dinit in a third — all side by side on the same host, regardless of
what the host itself uses. It's one of the reasons `--init` is
useful even on immutable or unusual distros: each container brings
its own init, on top of the same host.

It also means a busybox-init Alpine container runs happily on a
systemd Fedora host, and vice versa.

## Limitations vs bare-metal

An init system inside a container is **more limited** than the same
init system on a real machine:

- It can't manage host hardware (`systemctl` sees only container
  devices, no real hardware units).
- Host processes aren't visible (due to the PID namespace), so
  system-wide introspection is limited.
- Some units that conflict with host mounts are masked automatically
  at setup to avoid clobbering the host.
- Performance/power management, fstab mounting, and similar
  bare-metal concerns are out of scope.

That said, for what containers actually need — starting and
supervising services, running daemons, up, deps between units — they
do their job fine and good enough.

## Managing services with otter service

Because init systems differ so much, otter provides `otter service`
to manage services with one uniform interface:

```sh
otter enter my-box
otter service start sshd
otter service enable sshd
otter service status sshd
otter service restart sshd
otter service stop sshd
```

Supported actions: `start`, `stop`, `restart`, `status`, `enable`,
`disable`.

### How it works

`otter service` is a **thin wrapper**, not a full implementation: it
dispatches each action to the container's real native command based
on the detected init system — `systemctl`, `rc-service`/`rc-update`,
`/etc/init.d`/`update-rc.d`, a Slackware-style `rc.<name>` script,
`sv`, or `dinitctl` — and passes the real exit code straight back.
It never normalizes behavior or output across them, so `status`'s
output is whatever the underlying tool reports.

On a container with no init system it prints a message and exits `0`;
on a generic-init container it points you to a supported init and
exits non-zero.

### Example — sshd on systemd

```sh
otter create --init --image fedora ssh-box
otter enter ssh-box
```

Inside the container:

```sh
otter service enable sshd
otter service start sshd
otter service status sshd
```

## Notes

- `--init` implies `--unshare-groups` and `--unshare-process`.
- Official otter images already include an init system where the
  distro supports it, so `--init` usually needs no extra packages.
- `otter doctor` reports the live status of the container's init
  system (`systemctl is-system-running`, `rc-status`, `dinitctl status
  boot`, etc.).
- `otter service` is a convenience wrapper — it doesn't reimplement
  or normalize service management.
