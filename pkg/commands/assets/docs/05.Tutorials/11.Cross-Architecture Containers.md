# Cross-Architecture Containers

Otter normally runs containers of your host's architecture — an x86_64
host runs amd64 containers, an ARM host runs arm64 containers. But
your container manager can also run a container for a *different*
architecture than the host, transparently emulating the foreign
architecture with **qemu**. This lets you, for example, run an arm64
Debian container on an amd64 host.

## Supported architectures

Otter's images are built and supported for **amd64** and **arm64**
only. These are the two architectures otter ships images for, and
they're the only ones supported:

- `linux/amd64` — x86_64
- `linux/arm64` — aarch64

Support for any other architecture (RISC-V, s390x, 32-bit x86, etc.)
is **not planned**. Pick one of the two supported ones for
cross-architecture containers.

Note that not every image ships both architectures — check the
architecture column for a given image (see Images) before creating
a cross-arch container from it.

## Host prerequisites

For a cross-arch container to work, your container manager needs to
be able to *execute* foreign-architecture binaries. This requires
QEMU userspace emulation available on the host. Otter expects you to
have these installed and configured:

- `qemu-user-static` — the static qemu user-mode emulation binaries
- `binfmt-support` (or the equivalent binfmt_misc registration on
  your distro) — so the kernel knows to route foreign binaries to
  qemu automatically

On most distros:

```sh
sudo apt install qemu-user-static binfmt-support    # Debian/Ubuntu
sudo dnf install qemu-user-static                   # Fedora (binfmt handled at kernel level)
sudo pacman -S qemu-user-static binfmt-support      # Arch
```

These must be installed and the binfmt handlers registered on the
**host** before your container manager can reliably pull and run a
foreign-arch image — if they're missing, the container manager will
either fail to pull the right image or fail to exec inside it. The
same requirement applies whether you use Podman, Docker, or nerdctl.

## Creating a cross-arch container

Otter has a dedicated `--platform` flag on `otter create` to target
a different architecture — no extra container-manager flags needed:

```sh
otter create --image debian my-arm64-box --platform linux/arm64
```

`--platform` sets the image's target platform (e.g. `linux/arm64`)
and the request is handed to the container manager, which pulls the
arch-appropriate image variant and uses qemu for execution.

With the container manager's binfmt/qemu setup in place, everything
else is business as usual:

```sh
~$ uname -m
x86_64
~$ otter create --image debian my-arm64-box --platform linux/arm64
~$ otter enter my-arm64-box
user@my-arm64-box:~$ uname -m
aarch64
```

## How it works

When your container manager creates a container for a foreign
architecture, it:

1. Pulls the `linux/arm64` variant of the image (the image must ship
   that architecture — multi-arch images resolve automatically).
2. Registers/handles qemu userspace emulation via your host's
   `binfmt_misc` setup, so every command inside the container is
   translated by qemu.
3. Runs the container normally, just emulated.

The container's userspace (packages, binaries, libraries) is entirely
foreign-arch, while the kernel remains the host's — which is why
everything works through qemu emulation rather than natively.

As with regular containers, you cannot install foreign-arch **kernel
modules** — the kernel is still the host's.

## Other architectures (experimental)

Otter officially supports only amd64 and arm64. If you really want to
run a container for some *other* architecture to test things, there's
an **experimental** way to do it — but keep these three things in
mind:

1. **It's not guaranteed to work, and it's not officially supported.**
   If it breaks, there's no support obligation; you're on your own.
2. **Official otter images won't work with it**, and extending them to
   other architectures is not planned — they will remain amd64/arm64
   only.
3. **Third-party images that support the architecture will work fine
   as normal.** This path is really only useful with upstream images
   that already ship the arch you want.

You do this by passing the `--platform` flag straight through to your
container manager with `--additional-flags`, much like distrobox
users do:

```sh
otter create --image debian:stable my-riscv-box \
  --additional-flags "--platform=linux/riscv64"
```

This example command doesn't use official images because it
won't work for them; this is why it's using the upstream image.

The host-side requirements are the same as for the supported
architectures: `qemu-user-static` plus working binfmt registration
for the target architecture on the host. Beyond that, everything otter
does (enter, export, host-exec, etc.) works identically — the
container is just a normal otter container to every other command.

## Performance expectations

Emulation is slower than native execution — expect a noticeable
performance penalty for CPU-heavy workloads, since every instruction
goes through qemu translation. The emulated container is fine for:

- Testing software on a foreign architecture.
- Building/checking distro packages for another arch.
- Running lightweight services and tooling.

It's not a substitute for real ARM hardware for performance-sensitive
work.

## Notes

- Only `linux/amd64` and `linux/arm64` are supported; other
  architectures are not planned.
- Individual images may only ship one architecture — check before
  creating a cross-arch container.
- The host needs `qemu-user-static` + working binfmt registration for
  reliable cross-arch containers.
- Usage is identical to any other otter container beyond creation:
  enter, export, host-exec, etc. all work the same.
