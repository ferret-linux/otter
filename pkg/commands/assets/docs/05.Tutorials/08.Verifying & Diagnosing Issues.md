# Verifying & Diagnosing Issues

When something feels wrong inside an otter container — commands aren't
working, host integration is broken, or something just behaves
unexpectedly — `otter doctor` is the first thing to run. It checks
the container's health without making any changes and gives you a
clear picture of what's working and what isn't.

## Running doctor

Enter your container and run:

```sh
otter enter my-box
otter doctor
```

`doctor` runs a fixed set of read-only checks against the current
container and prints one `[OK]`/`[WARN]`/`[FAIL]` line per check.
It never modifies anything — it only reads container state and runs
read-only status commands.

## What doctor checks

| Check                | What it does                                                         |
| -------------------- | -------------------------------------------------------------------  |
| `container`          | Confirms you're actually inside a container                          |
| `borked`             | Detects if an error occurred during container setup                  |
| `ready`              | Checks that the container finished initialization                    |
| `official`           | Whether the image is an official otter image (informational)         |
| `root-mode`          | Rootful or rootless container (informational)                        |
| `host-spawn`         | `host-spawn` is present and meets the minimum version                |
| `run-host`           | The `/run/host` mount bridge is alive                                |
| `network`            | Network reachability (informational — offline use may be intentional)|
| `env-vars`           | Required identity environment variables are set                      |
| `core-scripts`       | All core otter scripts are present and executable                    |
| `init-system`        | Init system health (only for init-enabled containers)                |
| `custom-home`        | Custom home directory exists with correct ownership                  |
| `user-settings`      | Container user resolves correctly                                    |
| `lock`               | Whether the container is locked (informational)                      |
| `integration-sockets`| Host integration sockets (Wayland, PulseAudio, D-Bus) are mirrored   |

## Reading the output

Every check ends with one of three statuses:

- **`[OK]`** — everything is fine.
- **`[WARN]`** — informational or non-critical. These never affect
  the exit code. Examples: non-official image, offline network,
  locked container, non-init container.
- **`[FAIL]`** — something is broken. These cause `doctor` to exit
  with a non-zero code.

A clean run looks like this:

```sh
$ otter doctor
[OK] container: running inside a container
[OK] borked: container is not borked
[OK] ready: container is ready and bootstrapped
[OK] official: official otter image
[OK] root-mode: rootless container
[OK] host-spawn: v1.6.2 (>= v1.6.2)
[OK] run-host: /run/host is mounted
[OK] network: network is reachable
[OK] env-vars: CONTAINER_ID and OTTER_HOST_UID are set
[OK] core-scripts: all core scripts present and executable
[OK] init-system: systemd: running
[OK] custom-home: no custom home configured
[OK] user-settings: noel resolves correctly (uid 1000)
[OK] lock: container is not locked
[OK] integration-sockets: all detected host integration sockets are mirrored
```

## Fixing problems

The approach depends on what's failing:

### Issues an update and restart can fix

If `core-scripts` are failing, the container's internal scripts may
simply be out of date. `otter upgrade` resynchronizes otter's
internal scripts (like `otter-init`, `otter-export`, etc.) with the
current version on your host:

```sh
otter upgrade my-box
otter restart my-box
```

After restarting, the scripts are reloaded and the issue is often
resolved.

If `host-spawn` is outdated (doctor says it's an older version than
required), `otter upgrade` won't fix it — `host-spawn` is updated by
`otter-init` at container start time. A restart is enough:

```sh
otter restart my-box
```

`otter-init` will detect the old version and fetch the latest during
the next boot.

### Issues that require a new container

If doctor still shows `[FAIL]` after an upgrade and restart, the
container itself may be in a bad state. The most reliable fix is
to remove and recreate it:

```sh
otter remove my-box
otter create --image fedora my-box
```

This is especially true for:

- **`borked`** — the container failed during setup and can't recover.
- **`ready`** — the container never finished initialization.
- **`run-host`** — the mount bridge is broken and can't be repaired
  from inside.
- **`integration-sockets`** — host sockets are stale and the init
  system can't recover them.

When recreating, your home directory contents are preserved by default
(unless you pass `--rm-home`), so you won't lose your files.

### When to recreate vs. troubleshoot

| Situation                                   | Action                                        |
| ------------------------------------------- | --------------------------------------------  |
| `core-scripts` out of date                  | `otter upgrade` + `otter restart`             |
| `host-spawn` outdated                       | `otter restart` — `otter-init` updates it     |
| `init-system` unhealthy (e.g. systemd)      | `otter restart` — usually resolves on its own |
| `borked` or `ready` failing                 | Recreate the container                        |
| `run-host` not mounted                      | Recreate the container                        |
| `integration-sockets` stale                 | `otter restart` first; recreate if it persists|
| `custom-home` ownership wrong               | Fix ownership with `chown` on the host        |

## Notes

- `doctor` is read-only and safe to run anytime — it won't change
  your container.
- Some checks are informational only (official image, root mode,
  network, lock status) and won't cause a `[FAIL]` even if they
  report `[WARN]`.
- Init-system checks only run when the container was created with
  `--init`. On non-init containers, this check is reported as
  informational.
- `doctor` exits with code 0 only when every non-informational check
  passes.
