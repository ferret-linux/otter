# Automating & Scripting Otter

Otter is a CLI-first tool with a few features that make it
script-friendly: single-shot enters, JSON output, batch operations,
machine-safe color handling, and (from inside a container) ways to
reach the host. This tutorial collects the patterns.

## One-shot commands without a TTY

`otter enter ... -- cmd` runs a single command and returns, without
needing an interactive terminal when combined with `--no-tty`:

```sh
otter enter ci-box --no-tty -- cargo test
```

The container auto-starts if stopped, so this works in cron, CI,
and pre-commit hooks alike. Exit codes carry through the container.

## Machine-readable listings

`otter list --json` emits a JSON array of `{id, name, status,
image}`, sorted by name — ideal for scripts:

```sh
otter list --json | jq -r '.[].name'
otter list --json | jq -r '.[] | select(.status=="running").name'
```

Combined with `NO_COLOR=1` (disables ANSI output for piping),
list-based automation is stable.

## Batch operations

Most lifecycle commands take comma-separated names or `--all`, and
attempt every name even if one fails, ending with a summary:

```sh
otter start web,api,worker
otter stop --all
otter upgrade --all --running
otter remove --force legacy-1,legacy-2
```

See `otter start`, `otter stop`, `otter upgrade`, and `otter remove` for
the per-command details.

## Logs for supervision

`otter journal` shows a container's manager logs with familiar
flags — `--follow`, `--tail`, `--since`, `--until`, `--timestamps`:

```sh
otter journal --follow web
otter journal --since 30m worker
```

Tail a service or feed it into a supervisor. See `otter journal`.

## Reaching the host from inside a container

Inside a container, `otter host-exec` runs a command on the real
host (via the `host-spawn` helper otter installs automatically):

```sh
otter host-exec systemctl --user restart syncthing
```

`otter redirect` makes that a first-class host command *inside* the
container — not port forwarding, but a wrapper that runs the host
program transparently:

```sh
otter redirect add --host-cmd flatpak
flatpak --version   # now runs the host flatpak
```

See `otter host-exec` and `otter redirect`.

## Declarative provisioning

For reproducible machines, express containers as TOML and drive
them with `otter assemble` — `--file` even accepts a URL, so you can
bootstrap a machine from a repo:

```sh
otter assemble create --file https://example.org/setup.toml
otter assemble remove --file setup.toml
```

Creation is transactional: on failure, a just-created container is
rolled back automatically. See `Declarative Manifests & Assemble`.

## Some scripted examples

Back up your running containers to a dated tar:

```sh
for box in $(otter list --json | jq -r '.[].name'); do
  podman commit "$box" "backup/$box:$(date +%F)" || exit 1
done
podman save -o "backups-$(date +%F).tar" \
  $(podman images --format '{{.Repository}}:{{.Tag}}' \
    | grep '^localhost/backup/')
```

Run a test in every running container:

```sh
otter list --json | jq -r '.[] | select(.status=="running").name' \
  | while read -r box; do
      if otter enter "$box" --no-tty -- \
          sh -c 'command -v pytest && pytest -q'; then
        echo "$box ok"
      else
        echo "$box skipped"
      fi
    done
```
