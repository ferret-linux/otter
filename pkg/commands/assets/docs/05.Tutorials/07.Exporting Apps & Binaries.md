# Exporting Apps & Binaries

One of the most useful things about otter containers is the ability to
export applications and binaries from inside a container so they
appear and behave like native host apps — appearing in your app
launcher, running from the terminal, and being managed as part of
your normal desktop.

## Exporting a GUI application

Suppose you've installed Firefox inside your otter container and want
to launch it from your host's app menu without entering the container
first.

Inside the container:

```sh
otter export --app firefox
```

This does three things:

1. Finds Firefox's `.desktop` file inside the container.
2. Rewrites its `Exec=` line to route through `otter enter`, so
   launching it actually runs inside the container.
3. Copies the icon and writes the modified desktop entry to
   `~/.local/share/applications` on the host.

After this, Firefox shows up in your host's application launcher
just like a natively installed app. The entry includes an "(on
\<container\>)" label in its display name so you can tell it's from
a container.

You can also pass the path to a `.desktop` file directly if name
matching doesn't find it:

```sh
otter export --app /usr/share/applications/org.mozilla.firefox.desktop
```

### Removing an exported app

From inside the container:

```sh
otter export --app firefox --delete
```

Or from the host, right-click the app in your launcher and choose
the **Remove** action — every exported app gets one automatically.

## Exporting a binary

Sometimes you don't want a desktop entry, you just want a command
available on your host PATH that transparently runs inside the
container.

Inside the container:

```sh
otter export --bin /usr/bin/htop
```

This writes a small wrapper script to `~/.local/bin/htop-<container>`
on the host. Now typing `htop` on the host runs it inside the
container transparently.

### Custom names

If the default `<binary>-<container>` name doesn't suit you, use
`--as`:

```sh
otter export --bin /usr/bin/htop --as htop-custom
```

### Exporting with elevated privileges

If the binary needs root inside the container:

```sh
otter export --bin /usr/bin/docker --sudo
```

`--sudo` tries `sudo`, then `doas`, then `su-exec root` depending
on what's available in the container.

### Changing the export location

Binaries default to `~/.local/bin`. To put them somewhere else:

```sh
otter export --bin /usr/bin/htop --export-path ~/.local/bin-custom
```

## Listing exports

See what's been exported from the current container:

```sh
otter export --list-apps
otter export --list-binaries
```

## Declarative exports with manifests

If you prefer to declare what to export up front rather than doing
it manually, otter's manifest system supports this. In your
`otter.yml`:

```yaml
exported.apps = ["htop"]
exported.bins = ["/usr/bin/htop", "/usr/bin/git"]
```

When you run `otter assemble`, these exports are created
automatically during container setup. This is especially handy when
you're setting up a fresh machine — one command provisions the
container and all its exports.

## How otter export differs from distrobox

Distrobox uses `distrobox export --app` and `distrobox export --bin`
with a similar concept, but otter's implementation has a few
advantages:

- **`--sudo` support** — export binaries that need root inside the
  container without extra setup.
- **`--export-label`** — customise the "(on \<container\>)" label
  suffix, or disable it with `none`.
- **`--extra-flags`** — pass additional flags to the exported command
  itself (not to `otter enter`).
- **Manifest integration** — declare exports in `otter.yml` and have
  `otter assemble` create them automatically.
- **Auto-cleanup** — `otter remove` finds and removes everything
  exported for a container by scanning internal markers, so you never
  leave orphaned desktop entries or wrapper scripts behind.

## Notes

- `otter export` must be run **inside** the container, not on the
  host.
- Must **not** be run as root — it needs to resolve your real user's
  home directory.
- `--app` and `--bin` are mutually exclusive — pass exactly one.
- `--bin` refuses to overwrite a destination file that wasn't created
  by a previous `otter export --bin` (to protect real host binaries
  from accidental clobbering). Use `--as` to export under a different
  name if the default collides.
- Exported binaries are tagged with internal marker comments
  (`# otter_binary`, `# name: <container>`) — this is how `otter
  remove` and `--list-binaries` know what belongs to which container.
