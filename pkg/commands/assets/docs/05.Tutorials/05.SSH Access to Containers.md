# SSH Access to Containers

Otter containers share the host's network namespace by default, which
means you can SSH into them from the host (or from other machines) by
forwarding a port. This tutorial covers setting up SSH inside an
otter container, connecting to it, and forwarding X11 displays over
SSH.

## Prerequisites

- An otter container with an init system (`--init`) so that `sshd`
  can be managed as a service.
- The `openssh-server` package installed inside the container.

## Setting up SSH

### Create a container with systemd

```sh
otter create --init --image debian \
  --additional-packages "openssh-server" \
  ssh-box
```

### Enable and start sshd

Enter the container and enable the SSH daemon:

```sh
otter enter ssh-box
```

Inside the container:

```sh
sudo systemctl enable --now sshd
```

If you're using a non-systemd init system, start sshd manually:

```sh
sudo sshd
```

### Set a password or add your SSH key

By default, otter containers may not have a password set for your
user. You'll need one (or an SSH key) to authenticate.

**Option A — set a password:**

```sh
sudo passwd $(whoami)
```

**Option B — use your host's SSH public key:**

Your host's home directory is shared with the container, so your SSH
keys are already accessible:

```sh
mkdir -p ~/.ssh
cat ~/.ssh/id_ed25519.pub >> ~/.ssh/authorized_keys
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

## Connecting

Since otter containers share the host's network by default, the
container's ports are directly accessible on `localhost`. You just
need to pick a port (or let sshd use the default 22):

```sh
# From the host (or anywhere with network access)
ssh -p 22 your-user@localhost
```

If you're running multiple containers with sshd, give each one a
different port. Inside the container, edit `/etc/ssh/sshd_config`:

```sh
# Inside the container
sudo sed -i 's/#Port 22/Port 2222/' /etc/ssh/sshd_config
sudo systemctl restart sshd
```

Then connect from the host:

```sh
ssh -p 2222 your-user@localhost
```

### Port forwarding at creation time

You can also forward a port directly when creating the container, so
you don't have to change sshd's port inside:

```sh
otter create --init --image debian \
  --additional-packages "openssh-server" \
  --volume 2222:22 \
  ssh-box
```

Then connect with:

```sh
ssh -p 2222 your-user@localhost
```

## X11 forwarding over SSH

If you want GUI applications launched inside the container (via SSH)
to display on your host's X server, you need X11 forwarding.

### On the host

Make sure `xauth` is installed on the host:

```sh
# Debian/Ubuntu
sudo apt install xauth

# Fedora
sudo dnf install xorg-x11-xauth

# Arch
sudo pacman -S xorg-xauth
```

### On the container

Install `xauth` inside the container too:

```sh
sudo apt install xauth    # Debian/Ubuntu
sudo dnf install xorg-x11-xauth  # Fedora
```

And make sure X11 forwarding is enabled in sshd — it is by default,
but verify:

```sh
grep X11Forwarding /etc/ssh/sshd_config
# Should show: X11Forwarding yes
```

### Connect with X11 forwarding

```sh
ssh -X -p 22 your-user@localhost
```

Or for trusted forwarding (faster, less secure):

```sh
ssh -Y -p 22 your-user@localhost
```

Once connected, any GUI app you launch from that SSH session will
appear on your host's display:

```sh
# Inside the SSH session
xclock
firefox
```

### Forwarding Wayland

X11 forwarding over SSH only works with X11. For Wayland, you'll need
to use `otter enter` directly, which already handles the XDG runtime
and D-Bus session forwarding automatically.

## Using a non-default shell over SSH

If your container's default shell isn't one of the four otter supports
(bash, zsh, fish, nu), you can still SSH in — SSH uses whatever shell
is set in `/etc/passwd` for your user. To change it:

```sh
# Inside the container
sudo chsh -s /bin/zsh $(whoami)
```

Then reconnect with SSH.

## Troubleshooting

### "Permission denied (publickey)" or "Permission denied (password)"

- Make sure you set a password (`passwd`) or copied your SSH key into
  `~/.ssh/authorized_keys` inside the container.
- Check permissions: `~/.ssh` should be `700`, `authorized_keys`
  should be `600`.
- If using key auth, ensure `PubkeyAuthentication yes` is set in
  `/etc/ssh/sshd_config` (it is by default).

### "Connection refused"

- sshd might not be running. Check with `sudo systemctl status sshd`
  or `sudo sshd -t` to test the config.
- The port might be different than expected — check
  `/etc/ssh/sshd_config` for the `Port` directive.

### "Host key verification failed"

This happens when the host key changes (e.g. after container
recreation). Remove the old key:

```sh
ssh-keygen -R "[localhost]:22"
```
