# Desktop Environments & Window Managers

A container manager isn't just for CLI tooling — the same
host-integration primitives that make `otter enter` feel like a real
shell also make it possible to run a full desktop environment or
window manager from inside a container, launched straight from your
login manager. This is useful if your host tracks a stable-release
distro (Debian, an LTS Ubuntu, a RHEL family member) but you want to
run a much newer GNOME, KDE Plasma, or a standalone compositor like
Hyprland without giving up your host's stability.

This tutorial is adapted from distrobox's own "Run latest GNOME, KDE
Plasma, and Hyprland" write-up, credited in otter's
README, with the steps
re-worked around otter's actual mechanics rather than distrobox's.

⚠️ **Experimental territory.** Booting a full desktop session out of a
container is not otter's primary use case, and the DE/WM side of this
(package group names, session-manager quirks, compositor startup
flags) is entirely upstream behavior otter has no control over. Treat
this as a starting point, not a guaranteed-working recipe for every
distro/DE combination.

## Why this needs less manual plumbing under otter

distrobox's original guide spends most of its length on host-side
workarounds: fixing `/tmp/.X11-unix` ownership by hand, wiring up
`kactivitymanagerd` in `~/.profile`, manually bind-mounting `/dev/dri`,
`/dev/input`, and the D-Bus system socket. Most of that is either
unnecessary or handled differently under otter:

- **`/tmp` is bind-mounted from the host directly** (`/tmp:/tmp`), not
  recreated inside the container, so `/tmp/.X11-unix` already has the
  same ownership as on the host. Combined with otter's default
  rootless containers running as your own UID (`keep-id`), there's no
  ownership mismatch to fix — the `chown`-on-login workaround the
  original guide describes doesn't apply here.
- **`/dev` and `/sys` are bind-mounted by default** (unless you pass
  `--unshare-devsys` to otter create), so `/dev/dri`
  and `/dev/input` are already present inside the container — no
  `--additional-flags "--device ..."` equivalent needed.
- **`--init` gets you a real systemd user session, with sockets synced
  automatically.** This is the biggest difference from distrobox. If
  you create the container with `--init`, otter enables lingering and
  starts a genuine `user@<uid>.service` inside the container, and a
  companion integration unit symlinks the *host's* Wayland, Pipewire,
  D-Bus (session), dconf, GnuPG, keyring, p11-kit, and at-spi sockets
  into the container's own `$XDG_RUNTIME_DIR` — and re-syncs every 60
  seconds in case a socket appears later. This is what the original
  guide's manual X11 permission fix and `kactivitymanagerd` autostart
  hack are both working around by hand.

None of this is a hard requirement — you can skip `--init` if you'd
rather keep things closer to the original guide's shape — but it's
why the steps below look shorter than distrobox's.

## Using a stable host with a newer desktop

The rest of this guide follows the same shape as the original: pin a
newer, rolling-release distro inside a container to get a current
GNOME or Plasma, while your host stays on whatever stable release it's
on.

### Setting up the container

```sh
otter create --init --image fedora-rawhide gnome-de
```

A few things worth calling out about this one line, compared to
distrobox's equivalent (`distrobox create --init --additional-packages
"systemd" --image registry.fedoraproject.org/fedora:rawhide`):

- `fedora-rawhide` is a short name resolved against
  otter's registry, not a full
  image reference — it currently maps to
  `quay.io/fedora/fedora:rawhide`, otter's own build of Fedora
  Rawhide.
- Unlike the plain upstream Fedora Rawhide image the original guide
  pulls, otter's own `fedora-rawhide` image already bakes in `systemd`
  at build time, so there's no need for an `--additional-packages
  "systemd"` equivalent — official otter registry images
  ship with an init system pre-installed specifically so
  `--init` doesn't need extra package handling.
- `--init` implies `--unshare-groups` and
  `--unshare-process`, and is what unlocks the automatic
  socket-integration behavior described above.

Enter it once to let setup finish:

```sh
otter enter gnome-de
```

## Running Latest GNOME

Install the desktop group from inside the container, same as on a
native Fedora install:

```sh
[gnome-de]$ sudo dnf group install gnome-desktop
```

(Fedora's group names do shift between releases — if that exact group
id doesn't resolve, `dnf group list` inside the container will show
the current one.)

### Generate a session file

Because `/tmp/.X11-unix` ownership already matches the host (see
above), the only thing left is a session file on the **host's** side
so your login manager (GDM, SDDM, etc.) can find it. Create:

`/usr/local/share/wayland-sessions/otter-gnome.desktop`
(or `/usr/share/xsessions/otter-gnome.desktop` if your login manager
doesn't pick up the former):

```ini
[Desktop Entry]
Name=GNOME on Wayland (gnome-de otter container)
Comment=This session logs you into GNOME, running inside an otter container
Exec=/usr/local/bin/otter enter -T -- gnome-session
Type=Application
DesktopNames=GNOME
X-GDM-SessionRegisters=true
```

`-T` is otter's `enter` — it runs the
command without a pseudo-TTY, which is the right mode for something a
login manager launches directly rather than an interactive terminal
session. `/usr/local/bin/otter` assumes the default `make install`
location; adjust it if you installed otter somewhere else — see
installation.md.

Note this desktop entry doesn't name the container explicitly, so
it'll use whatever otter's configured default container is; add the
container name as an argument (`otter enter -T gnome-de -- gnome-session`)
if you have more than one otter container around, or set it explicitly
to be safe regardless.

Log out, and the new session should show up on your login screen.

## Running Latest Plasma

Same container, same pattern — install the Plasma group:

```sh
[gnome-de]$ sudo dnf groupinstall KDE
```

### Generate a session file

`/usr/local/share/wayland-sessions/otter-plasma.desktop`
(or the `xsessions` equivalent):

```ini
[Desktop Entry]
Exec=/usr/local/bin/otter enter -T gnome-de -- /usr/libexec/plasma-dbus-run-session-if-needed /usr/bin/startplasma-wayland
DesktopNames=KDE
Name=Plasma on Wayland (gnome-de otter container)
```

### If Plasma needs a hand starting `kactivitymanagerd`

The original guide adds `kactivitymanagerd` to `~/.profile` because
distrobox containers have no session/init manager of their own to
autostart it. With `--init`, this container has a real systemd user
session, so Plasma's own autostart mechanism (`~/.config/autostart` or
its own systemd user units, depending on how your Plasma packaging
ships it) should generally handle this without help — that's specific
to how Plasma's own packages are built for Fedora, not something
verifiable from otter's own source, so it's worth trying without the
workaround first. If `kactivitymanagerd` still isn't running once
you're in a session, fall back to the original's approach and add it
to `~/.profile` inside the container:

```sh
if [ -f /usr/libexec/kactivitymanagerd ]; then
  /usr/libexec/kactivitymanagerd & disown
fi
```

## Running Latest Hyprland

Hyprland is standalone rather than a full DE, so it gets its own
container rather than reusing `gnome-de`. Since `/dev` is already
shared by default, the only extra thing this container needs beyond
otter's defaults is the D-Bus **system** bus socket (session-bus and
Wayland/Pipewire sockets are handled by `--init`'s socket integration,
same as above — the *system* bus is a separate, always-on socket that
integration doesn't touch):

```sh
otter create --init --image arch hyprbox \
  --volume /run/dbus/system_bus_socket:/run/dbus/system_bus_socket
```

`--volume` here is otter create's
direct equivalent of distrobox's `--additional-flags "--device ... -v
..."` — no need to route it through a generic passthrough flag, since
volume mounts are a first-class create option.

Install Hyprland inside it:

```sh
otter enter hyprbox
[hyprbox]$ sudo pacman -Sy hyprland
```

Then, either run it directly:

```sh
otter enter hyprbox -T -- Hyprland
```

or, to launch it from a login manager, use the same session-file
pattern as GNOME/Plasma above with
`Exec=/usr/local/bin/otter enter -T hyprbox -- Hyprland`.

As with the original guide, this requires no other Wayland session to
already be running on that seat. If you want Hyprland running
alongside an existing host session (e.g. on a second tty), give it a
runtime dir and Wayland display name that don't collide with the
host's, using otter enter's
`--add-env`:

```sh
otter enter hyprbox --add-env XDG_RUNTIME_DIR=/run/user/1000/hypr \
                     --add-env WAYLAND_DISPLAY=wayland-hypr \
                     -T -- Hyprland
```

Otherwise, apps launched from inside the container will attach to
whichever Wayland display they find first, which is rarely what you
want if two compositors are alive at once.

## Using apps from the host while inside a DE session

Once you're inside one of these container-based sessions, you'll
likely still want to launch things that live on the host rather than
in the container (a host-only app, checking on the host's own
containers, opening a link in the host's default browser). That's what
`otter host-exec` is for — run from
inside the container:

```sh
[gnome-de]$ otter host-exec firefox
```

The `xdg-open`/`flatpak` symlinks otter sets up inside every container
already route through this mechanism automatically, so "open with" and
similar system integrations mostly work without you needing to reach
for `host-exec` directly. See
exporting-apps-and-binaries.md if you'd
rather go the other direction — making a container app show up as a
normal entry in the host's own application launcher, via
`otter export`.
