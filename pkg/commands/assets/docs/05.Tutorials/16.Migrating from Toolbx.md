# Migrating from Toolbx

Toolbx (the `toolbox` command) is a thin front-end for Podman, so its
containers are ordinary Podman containers. There is **no** `otter
migrate` command, and there are no plans to add one — migration is a
manual process. You either recreate your containers fresh or reuse an
existing Toolbx container as the image for a new otter container. If
you just want a clean start, creating a native otter container is the
simplest path:

```sh
otter create --image fedora my-new-box
```

## Migrate an existing Toolbx container

Because Toolbx runs on Podman, you can snapshot a Toolbx container
exactly like any other Podman container — commit, remove, recreate:

**1. Commit the Toolbx container to an image.** Find the container
with `toolbox list` (or `podman ps -a`), stop it so the snapshot is
clean, then commit:

```sh
# find the container
toolbox list

# stop it before committing for a consistent snapshot
podman container stop my-toolbox

# commit it to a local image (--squash keeps the size down)
podman commit --squash my-toolbox localhost/my-toolbox-image:latest
```

**2. Remove the Toolbx container** once you no longer need it:

```sh
toolbox rm my-toolbox
```

**3. Create a new otter container from the committed image:**

```sh
otter create --image localhost/my-toolbox-image:latest new-box
```

Any full image reference (something containing `/` or `:`) is used
as-is, so the committed image is picked up straight from your local
image store. See Using Custom Images for how image resolution works.

### Caveats of reusing a Toolbx image

- **No registry support.** The committed image lives only in your
  local image store; it is not published to any registry.
- **Treated as a non-official image.** Otter will flag it as a
  third-party/non-official image, and your experience may vary since
  it lacks otter's pre-configured setup.
- **Slower one-time setup.** Because it isn't an otter-blessed image,
  start/enter do extra setup, so first boot is noticeably slower than
  with a native otter image.
- **Toolbx integration is not migrated.** Toolbx initialises its
  containers on entry through its own entrypoint and host-side config
  (`~/.config/toolbox`); none of that carries over. If the committed
  image retains Toolbx's entrypoint, recommit with
  `--change ENTRYPOINT=[]` if it ever gets in the way. Recreate any
  host integration you need with otter's own mechanisms (see Host
  Integration and Exporting Apps & Binaries).

If you don't need to preserve installed packages, prefer creating a
native container from an official otter image instead — it avoids all
of the above.

## Toolbx image-based setups

Toolbx images (e.g. `registry.fedoraproject.org/fedora-toolbox`,
`quay.io/toolbx-images/ubuntu-toolbox`, `quay.io/toolbx/arch-toolbox`)
are plain OCI images, so you can use them directly as full references
with `otter create --image`. To get proper otter setup out of the box,
prefer otter's own registry images by short name (`fedora`, `ubuntu`,
`arch`, ...) — see Images and Registry for how the catalog maps.
