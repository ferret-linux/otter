# Caveats & Considerations

Some of otter's design decisions trade off things other tools
prioritize differently. This page exists so you know what you're
getting before you rely on it.

## Sandboxing is not the priority

Otter's containers are integration-first, not isolation-first. The
host's filesystem, devices, and (by default) network and PID
namespaces are all made available inside the container — see below,
and otter-create's `--unshare-*`
flags if you want to peel some of that back. If your goal is a hard
security boundary between host and container, otter is not built for
that; look at a hardened/isolated-by-default tool instead.

## The host filesystem is mounted inside the container

Every otter container gets the host root filesystem bind-mounted at
`/run/host` (one mount per top-level directory instead of a single
`/:/run/host` bind on podman+runc specifically, for compatibility
reasons — see otter-create). Combined with
the shared home directory, this means code running inside an otter
container can read and write most of what your host user can. This is
intentional — it's what makes host integration (exported apps, shared
home, VS Code Remote-Containers, etc.) work — not a bug to be patched
later.

## Non-official images are slower to enter

Otter's own registry images (see images.md) come
pre-configured at build time: shells, sudo, locale/timezone, and the
otter directory layout are already in place. A custom or third-party
image doesn't have any of that baked in, so otter's container
entrypoint has to detect and set it up itself on first boot, and
otter-init also prints a one-time warning
that the image wasn't built by otter. Expect a noticeably slower first
`otter enter` on a non-official image compared to a registry one.

## Third-party images are best-effort

Otter is written to work with any OCI image, but only the images in
otter's own registry (images.md) are
tested and maintained to otter's expectations. Bringing your own image
works, and otter tries to adapt sensibly (see e.g. the shell-fallback
behaviour in FAQ), but you may hit
distro-specific gaps that otter's own images already work around.
Prefer an official image when you can.

## No plans for Lilipod or systemd-nspawn

Otter only targets OCI containers, driven through Docker, Podman, or
nerdctl. There's no support, and no roadmap, for Lilipod or
systemd-nspawn as backends.

## Not a 1:1 distrobox replacement

Otter builds on ideas and code from distrobox, credited in the
project README, but it isn't aiming for behavioural parity with it.
Where the two disagree on a design decision, expect otter to diverge
rather than match distrobox's behaviour.

## Goal is a working, integrated distro — not the smallest container

Otter & its images are not optimized for minimal image size or fastest
possible container startup. The goal is a container that behaves like
a real distro install with your host folded into it — closer to a second
machine than a disposable sandbox. If you want the smallest or quickest
possible container, that's a different tool's job.
