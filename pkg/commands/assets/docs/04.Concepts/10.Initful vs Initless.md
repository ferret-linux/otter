# Initful vs Initless

An otter container can run with a real **init system as PID 1**
(initful) or without one, under a lightweight keepalive loop
(initless). This is the single biggest structural choice you make
with `otter create`, and it mostly comes down to one question:
do you need daemons/services running inside the box?

## Initless (default)

Otter's default is to **not** run an init system. After first-boot
initialization the container just keeps a small process alive that
keeps host files in sync; sessions are started with `otter enter`
on demand.

- Perfect for interactive shells, CLI tools, and anything you
  run nohup-style — no overhead, nothing to supervise.
- No PID 1 to manage services: long-running daemons (a database,
  a web server, a background worker) won't be supervised and won't
  auto-restart.
- Process cleanup for sessions is handled by otter itself; the
  enter wrapper (`otter-subreaper`) reaps orphaned children so they
  don't pile up on the container's PID 1. See `Subreaper`.

## Initful (`--init`)

`--init` boots a real init system as PID 1 and hands it the
container. Otter detects and runs whichever of these the image
provides: **systemd**, **openrc**, **sysvinit**, **runit**, or
**dinit** (a generic fallback catches anything else).

- You get real service management: units/scripts can start
  sshd, postgres, a dev server, or run a cron-like schedule, and
  stay supervised.
- `--init` implies `--unshare-groups` and `--unshare-process`, so
  the container gets its own PID namespace (host processes become
  invisible from inside) and login happens through `su`.
- With systemd, host integration sockets (Wayland, PipeWire,
  D-Bus, ...) are mirrored into the container's own user session.
  See `Host Resource Sharing`.

## Choosing

| Need                                               | Pick               |
| -------------------------------------------------- | ------------------ |
| Interactive shell / CLI / one-shot scripts         | initless (default) |
| A long-running daemon (db, web server, sshd)       | `--init`           |
| You want systemd-style units or log control inside | `--init`           |
| Isolated PID view (hide host processes)            | `--init`           |

Initless is cheaper and simpler; initful is what you want as soon
as "something should keep running" enters the picture. You can mix
both in one machine — e.g. an initless dev box and an initful box
for the database.

## A naming trap

`--init` (init *system*) and `--init-hooks` / `--pre-init-hooks`
(container *initialization*) share a word but are unrelated.
`--init-hooks` runs shell commands during first-boot setup whether
or not an init system is present.
