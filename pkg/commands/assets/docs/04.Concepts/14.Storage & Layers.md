# Storage & Layers

Otter containers are built on top of container images managed by
the host's container manager (podman, docker, or nerdctl). This
page explains where data lives, what happens when you install or
remove things, and how storage behaves across the container
lifecycle.

## Where images come from

An image is the read-only base that a container is built from.
Otter pulls images from registries — either the built-in registry
system (short names like `fedora`, `arch`, `ubuntu`) or full
image references (anything containing `/` or `:`). Registry images
can be re-pulled at any time: if you delete one locally, `otter
create` will fetch it again on next use.

Local images — built with `podman build`/`docker build` or
committed from an existing container — live only on your host. If
you delete a local image, it's gone. There's no registry to
re-pull it from.

## What a container is

A container is a writable layer on top of its image. The image
itself is never modified — every file change (installed packages,
created configs, written data) goes into the container's own
writable layer. This layer is stored by the container manager,
typically under `~/.local/share/containers/` (podman) or
`/var/lib/docker/` (docker).

Otter stores its own metadata (init scripts, export markers,
host-exec helpers) alongside the container manager's data, under
`~/.local/share/otter/`.

## What happens to old images

Registry images: you can always re-pull them. Deleting a local
copy of `fedora` just means the next `otter create --image fedora`
will fetch it again.

Non-official and local images: if you delete them, they're gone
permanently. There's no registry to fall back to. If you've
committed a container to a local image and then delete that image,
the only recovery path is recreating from scratch.

## What `otter remove` does

`otter remove` (alias `otter rm`) deletes the container's
writable layer and all associated metadata: the otter init
scripts, export markers, desktop entry, and any binaries or apps
that were exported to the host. The base image is left untouched.

This is a permanent operation. The container's state — installed
packages, created files, modified configs — is gone. The only
recovery is creating a new container from the same image and
re-doing your setup. See `Backing Up, Cloning & Restoring` for
ways to preserve state before removal.

## Custom homes and removal

If the container was created with `--home`, `otter remove` leaves
the custom host directory intact by default. Pass `--rm-home`
(alias `-H`) to also delete it:

```sh
otter remove my-box           # custom home is preserved
otter remove --rm-home my-box # custom home is also deleted
```

There is a safety guard: otter refuses to remove home if the path
is empty, matches your real host home, or is a known dangerous
path like `/`, `/home`, or `/root`.

## Storage cleanup

Otter's built-in registry images are managed to prevent storage
clutter: stale layers and dangling images from official otter
images are cleaned up automatically. This does not apply to
local or non-official images — those stay until you explicitly
remove them with `podman rmi`/`docker rmi` or `podman system
prune`/`docker system prune`.

## App container vs system container

Most otter containers are "app containers" — they run a single
command (your shell) and exit when you're done. The container's
PID 1 is your shell, and there's no init system.

When you create a container with `--init`, it becomes a "system
container" — systemd runs as PID 1, manages services inside the
container, and the container stays running even when no user
session is active. This trades some host integration (you can no
longer see host processes from inside) for the ability to run
daemons, use `systemctl`, and have services auto-start.

This is not the same as a system container in the LXC/Incus
sense — those are full VM-like environments with their own kernel
interfaces, device management, and privileged service supervision.
Otter's system containers are a best-effort approximation: they
use systemd as init and the `--unshare-*` flags to carve out some
isolation, but they still run on the host kernel with the host's
devices and runtime directories shared. Think of it as "enough
init to run services," not "a lightweight VM."

See `Initful vs Initless` for the full tradeoff.

## Miscellaneous

- **`/dev/shm`** — shared memory is bind-mounted from the host
  by default. `--unshare-ipc` removes this, which also removes
  access to POSIX shared memory. See `Host Resource Sharing`.
- **tmpfs** — some container managers mount a tmpfs on `/tmp`
  and `/run` inside the container. Changes there don't persist
  across container restarts.
- **Overlay vs vfs** — rootless podman on kernels older than
  5.11 may fall back to the `vfs` storage driver, which is
  slower and uses more disk. See `Rootful vs Rootless`.
- **Space on host** — container data lives on the host
  filesystem. Use `podman system df` or `docker system df` to
  check how much space containers and images are using.
