# Security & Isolation

Otter is **integration-first, not isolation-first**. Its default
setup deliberately shares a lot with the host so containers feel
native, which means an otter container is not a sandbox boundary.
This page says what the defaults are, what the isolation knobs do,
and when (not) to reach for them.

## What's shared by default

By default an otter container gets:

- **The host filesystem** — your home directory is mounted at the
  same path, the entire host root is mounted at `/run/host`, and
  `/tmp` is shared. See `Host Resource Sharing`.
- **Devices and kernel interfaces** — `/dev` and `/sys` are
  bind-mounted.
- **Namespaces** — network, IPC, and PID namespaces are shared
  with the host (containers run with `--network host`, `--ipc
  host`, `--pid host`).
- **Relaxed isolation options** — containers are created
  `--privileged` with SELinux/AppArmor confinement disabled and no
  PID limit, and otter doesn't manage capabilities.

Pulling these back is exactly what the `--unshare-*` flags are
for; there is no scenario where otter starts stricter and you
loosen it.

## The isolation knobs

`otter create --unshare-*` (and the manifest equivalents) peel the
defaults back one namespace at a time:

- `--unshare-devsys` — don't bind-mount the host's `/dev` and
  `/sys`.
- `--unshare-ipc` — don't share the host IPC namespace (container
  gets its own `/dev/shm`).
- `--unshare-netns` — don't share the host network namespace
  (container gets its own network; hostname and
  `/etc/hosts`/`resolv.conf` are no longer synced from the host).
- `--unshare-groups` — don't forward your host group membership;
  entry logs in via `su` instead.
- `--unshare-process` — don't share the host PID namespace (host
  processes become invisible from inside).
- `--unshare-all` — enables all five at once.
- `--no-userns-limit` — for rootless Podman, drop the capped
  `keep-id:size=65536` user-namespace range and use a plain
  `keep-id` namespace instead.

Note that `--unshare-devsys` also removes direct host `/dev/kvm`
passthrough — see `Using KVM & Libvirt in Containers` for why.

## The trust model in practice

- The container shares the host **kernel**, so installing kernel
  modules inside the container is meaningless; the driver story is
  always "host kernel + container userspace".
- With rootful containers the "host access" line moves a lot closer
  to root — see `Rootful vs Rootless`. Keep untrusted workloads
  rootless.
- `--root` elevates via a real escalation program (sudo, doas,
  run0, pkexec), which is itself a trust decision you're making.
- Because home and `/run/host` are readable/writable by your user,
  anything inside the container can read and write what your host
  user can. Treat container code that you'd treat as untrusted local
  code.

## Recommendations

- Defaults are fine for development and daily use — most of what
  you install is no more or less dangerous inside the box.
- If you're running **untrusted** or third-party software and want
  an *approximate* reduction, use `--unshare-all` (optionally
  coupled with `--no-userns-limit`) and keep it rootless.
- If you need a **hard** security boundary, an otter container is
  the wrong tool: use a VM or a sandboxing tool built for that
  goal. Otter's container-vs-host relationship is deliberately not
  a fortress.
