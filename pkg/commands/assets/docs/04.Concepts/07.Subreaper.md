# Subreaper

`otter-subreaper` is a small helper that otter ships inside its
containers and uses when starting interactive `otter enter` / `otter
sh` sessions. It is completely transparent — you never run it or
configure it — but understanding it explains why sessions behave
correctly even when the container has no init system to clean up after
shells.

## What a subreaper is

On Linux, when a process is orphaned (its parent exits before it), the
kernel reparents it to the nearest "subreaper" ancestor, or to PID 1
if there is none. A process marks itself as a subreaper with the
`prctl(2)` `PR_SET_CHILD_SUBREAPER` call. Subreapers — not PID 1 —
then become responsible for reaping those orphaned children once they
exit, instead of letting them linger as zombies.

## Why otter uses one

Containers created with `--unshare-groups` (or `--unshare-all` or
`--init`, which imply it) are entered via `su` so the session performs
a real login as your user instead of inheriting host group
membership. Programs inside such a session sometimes double-fork and
detach — fish's background `fish_update_completions` worker is a
classic example. Without a subreaper, those detached descendants would
reparent to the container's PID 1, and the container is not guaranteed
to reap them (it may not even run an init system). `otter-subreaper`
sits between the session and PID 1 and takes over that responsibility
instead, so orphaned workers are reaped reliably and don't linger as
zombies.

## When it's active

Any time you enter a container created with `--unshare-groups`,
`--unshare-all`, or `--init`, `otter sh` / `otter enter` wraps the
login (`su`) in `otter-subreaper`. Plain rootless containers created
without those flags exec your shell directly and don't use the helper.

## How it works

The helper marks itself as a child subreaper, forks, and execs the
command you're running (`su`). Its own process stays alive, forwarding
the terminal signals a session needs (resize, interrupt, terminate,
job control) to the real child, and loops reaping whichever process
exits next — its own child or any reparented orphan. It deliberately
keeps the subreaper attribute on itself rather than on `su`, so `su`'s
own child and signal handling is never disturbed.

## Do you need to interact with it?

No. The helper lives read-only at
`/usr/lib/otter/scripts/otter-subreaper` inside the container and is
invoked automatically on enter. There is no configuration, flag, or
command associated with it. If a session ever appears unresponsive,
that points at the `--unshare-groups` login behavior itself — there is
no per-session knob for subreaper to tweak.
