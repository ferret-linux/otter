# Compatibility

## Host architecture

Otter's images are built and supported for **amd64** and **arm64**
only. Some individual images may only ship one of the two — check the
architecture column in `Images` for a given
image — but no image supports any architecture outside this pair.

## Container managers

Otter works with **Podman**, **Docker**, and **nerdctl**. One of the
three must be installed and working; otter auto-detects whichever is
available, or you can pin one explicitly via
`preferences.container-manager` in `otter.conf` (see `Configuration`).

Podman gives the most out-of-the-box experience for rootless use. If
you use rootless Docker or nerdctl instead, you're expected to have
configured rootless mode for them yourself — otter doesn't set that up
for you.

## Privilege escalation

For anything that needs root (`--root`), otter supports `sudo`,
`sudo-rs`, `doas`, `run0`, and `pkexec`. By default it autodetects one,
trying them in that order; you can pin a specific program via
`preferences.sudo-program` in `otter.conf`.

You are not supposed to use `sudo otter` or similar by convention;
`otter --root` is the official and only-supported way to use rootful
container management on otter.

## Init systems

Inside containers created with `--init`, **systemd** gets the most
testing. **OpenRC**, **dinit**, **sysvinit**, and **runit** are also
supported directly. Other init systems are handled through generic
`/sbin/init` support, without the init-specific integration the five
above get.

## GPU support

Otter has official, first-party support for the NVIDIA Container
Toolkit, detected automatically when it's set up on the host.

AMD and Intel GPUs don't need special handling, as they are already
handled by the kernel (on the host) and mesa packages (inside the
container). Nvidia is a special case due to out-of-tree kernel
modules and drivers.

## Host kernel requirements

The host kernel needs **cgroups v2** and **overlayfs** support. These
aren't optional extras — otter expects them to be available, and some
functionality and features that otter offers directly depend on these.

These are also generally requirements for Podman, Docker, and nerdctl;
most Linux distros already include them by default. (If you are using
any decent Linux distro you are good to go.)

## Image support tiers

Otter's built-in registry images are curated and otter-optimized —
see `Images`. Any other image (a full image reference, your own custom build,
or a distro not in the built-in catalog) will work,
but isn't held to the same bar: package sets, setup steps,
and helper integrations on third-party images may
not be as consistent as on official otter images, so expect a
possibly degraded experience.

## Recommended software versions

Otter may work with older versions, but the following are the
recommended minimum versions:

| Container manager | Version |
| ----------------- | ------- |
| **Podman**        | 4.0+    |
| **Docker**        | 24.0+   |
| **nerdctl**       | 2.3+    |

| OCI runtime | Version |
| ----------- | ------- |
| **crun**    | 1.20+   |
| **runc**    | 1.3+    |
| **youki**   | 0.6+    |

**crun 1.29.x is not recommended** due to PTY-related issues. Use a
version below 1.29.x or a newer fixed version.

## Host integration

Flatpak is not required for Otter itself. However, host-execution
features using `host-spawn` may require Flatpak's D-Bus integration
(`org.freedesktop.Flatpak`) to be available on the host.
This typically needs flatpak to be installed on host, you can skip it
if you don't use `otter host-exec` and `otter redirect` commands inside
the containers.
