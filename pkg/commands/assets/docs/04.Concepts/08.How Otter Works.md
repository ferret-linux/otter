# How Otter Works

Otter creates Linux "boxes" — OCI containers that behave like
native, integrated OS environments — and manages their whole
lifecycle for you: image selection, first-boot setup, entering,
starting/stopping, upgrading, and removing. This page is the
30-second mental model; every piece is expanded elsewhere.

## The big picture

`otter create` picks an image, creates a container, and runs
otter's own initialization inside it once. After that the
container is a normal, running environment: `otter enter` drops
you into a login shell, the `start`/`stop`/`restart` family
controls it like system services, and `otter remove` deletes it.
Everything rides on an OCI container manager (Podman, Docker, or
nerdctl), which otter drives for you.

## Images and the registry

Otter ships a catalog of optimized official images
(`ghcr.io/ferret-linux/<distro>-otr`) built from the Containerfiles
in the repository's `images/` directory. A short name
(`--image fedora`) is resolved from that catalog; anything
containing `/` or `:` is used verbatim, so you can point otter at
any OCI image — including one you committed locally yourself. See
`Images` and `Using Custom Images`.

## What a container is, physically

An otter container is a normal container plus otter's integration
layer:

- **Helper scripts** — `otter-init`, `otter-export`,
  `otter-host-exec` and friends are written into the container
  read-only under `/usr/lib/otter/scripts/`.
- **Host sharing** — your home directory is mounted at the same
  path, the whole host root is mounted at `/run/host`, and `/tmp`,
  `/dev` and `/sys` are shared by default. See Host Resource
  Sharing.
- **Labels** — `otter.*` labels record how the container was
  created (rootful, unshare flags, init system, image), which is
  what `otter inspect` and `otter list` detect.

## First boot: initialization

`otter-init` provisions base packages (shell, sudo, curl, ...),
creates the container user, sets locale and timezone, writes the
shell profile, wires up host-mount integration and GPU handling
(if selected), and runs your `--pre-init-hooks` / `--init-hooks`.
This is why the first start of a non-official image is slower.
Afterwards the container either keeps a small keepalive loop
(initless) or boots a real init system as PID 1 (`--init`). See
`Initful vs Initless`.

## Sessions

`otter enter` (alias `otter sh`) starts the container if it's
stopped, waits for setup to finish, then execs into it — mapping
your working directory, copying most of your host environment, and
attaching a PTY. In `--unshare-groups` containers the login runs
through `su` under the otter-subreaper wrapper, which keeps
orphaned background processes from piling up on the container's
PID 1. See `Subreaper` and `otter enter`.

## Lifecycle, batch, and declarative

`otter start`, `stop`, `restart`, `pause`, `unlock`, `remove` and
`upgrade` accept comma-separated names or `--all`, and otter
attempts every requested name even if one fails. `otter assemble`
creates or removes containers declared in a TOML manifest, and
`otter create --clone` duplicates an existing stopped container.
See `Declarative Manifests & Assemble`.

## Backend

Otter auto-detects Podman, Docker, or nerdctl and runs everything
through it, rootless by default; `--root` escalates through your
sudo/doas/run0/pkexec program. See `Rootful vs Rootless` and
`Compatibility`.

## Where things live

- `~/.config/otter/otter.conf` — your configuration.
- `~/.local/share/otter/` — otter's data directory.
- Inside each container `/usr/lib/otter/` — helper scripts, and
  the lock file for locked containers.

## The default prompt

Official images ship a [starship](https://starship.rs) prompt as their
default shell prompt. It is only active when **all** of the following
hold:

1. the image is official (`/usr/lib/otter/container.official` exists),
2. the `starship` binary is on your container's `PATH`,
3. the otter starship config exists (`/usr/lib/otter/helpers/starship.toml`),
4. `OTTER_DISABLE_STARSHIP_INTEGRATION` is **unset**, and
5. `/usr/lib/otter/container.no-starship` does **not** exist.

If any condition fails, the shell falls back to the toolbox-style otter
prompt (the `⬢`-mark P1/`fish_prompt`/`PROMPT_COMMAND`). Opting out also
clears `STARSHIP_CONFIG` so the starship config env set by official images
at build time doesn't linger ( user configs are unaffected ).

There are two supported ways to opt out and keep the otter prompt:

- **Temporarily, per session** — pass the env var on `enter`:

  ```sh
  otter enter my-box --add-env OTTER_DISABLE_STARSHIP_INTEGRATION=1
  ```

- **Persistently, per container** — create a marker file inside the
  container ( as root or esclated privilege ). This survives restarts
  and is untouched by `--add-env`:

  ```sh
  otter exec my-box -- sudo touch /usr/lib/otter/container.no-starship
  ```

  Remove the marker to re-enable starship:

  ```sh
  otter exec my-box -- sudo rm /usr/lib/otter/container.no-starship
  ```
