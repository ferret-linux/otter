`otter service` — manage a service inside the container, using
whichever init system the container actually runs.

## Where this runs

Like `otter-export`, `otter-host-exec`,
`otter-doctor`, and `otter-redirect`, this is
not a host command — it's run **inside** an otter container, via the
same container-side `otter` wrapper (`/usr/bin/otter` inside the
container) that dispatches to the real script at
`/usr/lib/otter/scripts/otter-service`.

In other words: `otter enter my-box`, then run `otter service ...`
from the shell you land in.

## Synopsis

```text
otter service <action> <name>
```

## Description

`service` is a convenience tool, not a full init-system
implementation: it dispatches each action to whichever real,
native command the container's own init system already uses, and
passes that command's real exit code straight back. It never
reimplements service management itself.

Supported actions (each with a short alias to match the rest of the
CLI):

| Action    | Alias | What it does                                        |
| --------- | ----- | --------------------------------------------------- |
| `start`   | `ex`  | Start the service now.                              |
| `stop`    | `kl`  | Stop a running service.                             |
| `restart` | `rbt` | Stop then start the service.                        |
| `status`  | `st`  | Show the service's current status.                  |
| `enable`  | `up`  | Make the service auto-start on boot/init.           |
| `disable` | `dn`  | Stop the service from auto-starting on boot/init.   |

Which real command an action maps to depends entirely on the
container's init system (`systemctl`, `rc-service`/`rc-update`,
`/etc/init.d`/`update-rc.d`, a Slackware-style `/etc/rc.d/rc.<name>`
script, `sv`, or `dinitctl`) — `service` never normalizes behavior
or output across them, so `status`'s exact output, and what counts
as a valid `<name>`, are whatever the real underlying tool reports.

On a container with no init system, `service` prints a message
explaining that and exits `0`. On a container whose init system
otter only supports generically (`container.initsystem` is
`generic`), `service` prints a message pointing to a supported init
system and exits non-zero, since there's no real tool for it to
dispatch to.

## Examples

```sh
otter service start sshd
```

Starts `sshd` using the container's real init system.

```sh
otter service enable sshd
```

Makes `sshd` start automatically the next time the container's init
system comes up.

```sh
otter service status sshd
```

Shows `sshd`'s current status, in whatever format the container's
real init system reports it.

## Notes

- `service` never invents its own success/failure semantics for a
  real dispatch (e.g. `systemctl`, `sv`, `dinitctl`) — its exit code
  is that command's own exit code, unchanged.
- `enable`/`disable` on Slackware-style sysvinit and on runit are
  otter's own direct filesystem operations (there's no separate tool
  for either), since neither has a native command for it; otter
  reports success or failure of that operation itself.
- A nonexistent `<name>` fails the same way the underlying tool or
  file lookup would on its own — `service` doesn't pre-validate that
  a service exists.
