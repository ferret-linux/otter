# Hidden APIs

Everything on this page is **internal and unstable**. It exists for the
Holt GUI bridge, generated launchers, and other automation shipped with
otter. These flags, JSON shapes, and aliases are not part of the stable
user interface: they are hidden from `--help`, may change or disappear
in any release, and are not covered by the usual compatibility promises.
Prefer the documented configuration keys and commands instead.

## Hidden global flags

These flags are accepted by the top-level `otter` command and are
inherited by every subcommand. Their defaults come from `otter.conf`.

| Flag | Alias | Purpose |
| ---- | ----- | ------- |
| `--sudo-command` | `-sc` | Override `preferences.sudo-program` for one invocation. |
| `--container-manager` | `-cm` | Override `preferences.container-manager` for one invocation. |

### `--sudo-command`, `-sc`

Any string is accepted syntactically. When root mode is active, the
value is validated: `autodetect` (the default) tries `sudo`, `sudo-rs`,
`doas`, `run0`, and `pkexec` in that order; `sudo` and `sudo-rs` are
checked with a probe; `doas`, `run0`, and `pkexec` are only checked for
existence. Any other value is accepted with a warning and is not
validated, so custom escalators must be verified by the caller. Passing
`--root=false` skips this validation for that invocation.

### `--container-manager`, `-cm`

Case-sensitive. Accepted values are `autodetect`, `podman`, `nerdctl`,
and `docker`; an empty value behaves like `autodetect`, which tries
Podman, then nerdctl, then Docker. An unrecognised value prints the
available choices and exits with status 1.

## Settings GUI bridge

`otter settings` normally opens the interactive terminal editor. Two
hidden flags switch it into a machine-readable mode used by Holt. If
both are supplied, `--list-json` wins.

### `--list-json`

Prints a pretty-printed JSON array to stdout. Every editable field
becomes an object with `section`, `field`, `kind` (`text` or `toggle`),
`value`, and `description`, plus `options` for validated selections and
`numeric` for numeric text fields. Section headers are omitted. Values
are strings for text fields and booleans for toggles.

### `--apply-json`

Reads a single JSON object from **stdin** — there is no file argument.
Keys are the bare field names, without their section prefix:

- text: `hostname`, `name`, `default`, `staleness-warn-threshold`,
  `staleness-autopull-threshold`, `shell`, `scripts-dir`,
  `container-manager`, `sudo-program`
- boolean: `init-system`, `rootful`, `userns-nolimit`, `no-entry`

`shell` must be one of `bash`, `zsh`, `fish`, `nu`, and
`container-manager` one of `autodetect`, `podman`, `docker`, `nerdctl`.
The two staleness fields accept numeric strings. Unknown keys, wrong
types, and out-of-range options reject the entire payload before
anything is written. On success otter saves the merged configuration to
the invoking user's own `otter.conf` atomically and prints `ok`.

## Inside-container command aliases

These are exposed by the scripts installed inside otter containers, not
by the host-side CLI. The long forms are documented with their commands
(`Export`, `Redirect`).

| Command | Alias | Long form |
| ------- | ----- | --------- |
| `otter export` | `-R` | `--refresh` — regenerate an existing export in place. |
| `otter redirect add` | `-c` | `--host-cmd` — command to run on the host. |
| `otter redirect add` | `-n` | `--as` — name for the wrapper in the container. |

`otter redirect` also accepts `--version`/`-V`. Note that `-R` means
`--running` for the host-side `upgrade` command and `--replace` for
`assemble`; it is not a global alias.

## Doctor's informational warnings

`Doctor` prints `[WARN]` lines that never change its exit status. In
addition to the informational checks named in its own page, these
warning branches can appear:

- `init-system`: `systemd: degraded`, `generic init has no structured
  status concept`, or `unrecognized container.initsystem value: <value>`
- `integration-sockets`: `OTTER_HOST_UID not set, cannot verify sockets`
  on initful containers, or `non-init container, nothing to check`

Treat them as diagnostics, not failures. See `Doctor` and
`Verifying & Diagnosing Issues` for the full check list.
