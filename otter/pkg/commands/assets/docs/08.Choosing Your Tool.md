# Choosing Your Tool

Otter is one of several ways to get a working Linux environment on
top of a host. This page helps you pick which one fits — and it
starts from the question people usually don't realise they're
answering: **are you worried about *mess* or *malware*?**

- **Mess** — package state cluttering your host, dotfiles leaking
  between projects, bleeding-edge or cross-distro packages that would
  destabilise a stable base you want to keep clean. This is what otter
  (and Toolbox and Distrobox) are built to solve.
- **Malware** — code you don't trust and want a real security
  boundary against. Container-based integration tools are **not** a
  boundary; for untrusted code reach for a sandbox or a VM instead.

If your goal is mess-free, integrated tooling, read on. If your goal
is isolation from untrusted code, otter is the wrong tool — see
`Security & Isolation` and the alternatives below.

## The landscape in one line each

- **Otter** — integration-first containers: a real distro userspace
  with your host home, devices, and resources folded in, plus exported
  apps, declarative manifests, and per-container state hygiene.
- **Toolbox** (Fedora) — the official, minimal Fedora container tool;
  mirrors your Fedora release, shares home and services, but has no
  custom home, no app export, no rootful mode, no declarative setup.
- **Distrobox** — the shape otter is modeled on: any-distro containers
  with host integration and app export, but full home sharing with no
  isolation story.
- **Flatpak** — sandboxed GUI apps with a real (if coarse) security
  boundary, curated store, and shared runtimes; not a general-purpose
  distro userspace.
- **Raw Podman/Docker** — full manual control over images, mounts, and
  namespaces; powerful but you wire up everything yourself.
- **Incus (VM)** — the strongest isolation short of physical separation;
  a whole OS with its own kernel. Heavy, but the only real boundary for
  untrusted code.

| Concern                              | Otter | Toolbox     | Distrobox      | Flatpak |

## Otter's position

Otter is about **state hygiene and integration, not security**. Its
defaults deliberately share the host filesystem, devices, and
namespaces so containers feel native (see `Host Resource Sharing` and
`Security & Isolation`). You get the ergonomics of a second machine —
shared home, exported GUI apps, per-project boxes — without giving up
control of where each container's state lives.

Reach for otter when you:

- run a stable or immutable base and want a scratch userspace for
  packages the host shouldn't carry;
- mix distro ecosystems (apt, dnf, pacman, AUR) side-by-side;
- want reproducible, manifest-defined environments (`otter assemble`);
- want per-project isolation of *state* (see `Custom Home` and the
  per-project tutorials) — again, hygiene, not a sandbox.

Reach for something else when you:

- need a hard boundary for untrusted code → **VM** or a hardened
  sandbox (Flatpak if it's a desktop app);
- want only curated, sandboxed desktop apps with no CLI/userspace
  needs → **Flatpak**;
- are on Fedora and want the absolute minimal, distro-mirroring option
  with nothing extra → **Toolbox**;
- need low-level control over images, mounts, and namespaces and don't
  want otter's conveniences in the way → **raw Podman/Docker**;
- must guarantee isolation and reproducibility to the point of a fresh
  kernel and boot → **VM**.

## Otter vs Distrobox

Otter is a **fork of Distrobox**. It started as a superset of it, but
has since evolved and will keep diverging — it has no official
compatibility with Distrobox or its containers. Notable differences:
a first-class image registry, TOML settings and manifests instead of
Distrobox's INI assemble files and plain image pulls.

### Commands available

- **Otter** — a single `otter` frontend with named subcommands:
  `create`, `enter`, `list`, `start`, `stop`, `restart`, `pause`,
  `rm`, `upgrade`, `export`, `host-exec`, `assemble`, `inspect`,
  `doctor`, `journal`, `service`, `settings`, `registry`, `redirect`,
  `generate-entry`, `documentation`.
- **Distrobox** — one tool per verb: `distrobox create`, `enter`,
  `list`, `stop`, `rm`, `upgrade`, `export`, `host-exec`, `assemble`,
  `ephemeral`.

### Scripting friendly

- **Otter** — machine-readable `--json` output on `otter list`,
  `otter inspect`, and `otter registry`, and non-interactive behavior:
  Only interactive prompt is `otter host-exec`'s first-time `host-spawn` install,
  which `--yes` skips.
- **Distrobox** — `distrobox ls` or similar work for scripting,
  but output is table/text only and there's no equivalent
  machine-readable surface.

According to me (biased) otter is much more script friendly & wrappable compared
to distrobox.

### Registry & image handling

- **Otter** — first-class `otter registry`: short names,
  enabled/disabled entries, staleness tracking (warn at `5` builds,
  auto-pull at `10`), and automatic cleanup of replaced/official
  images (local & non-official are left alone).
- **Distrobox** — pulls whatever image you name directly; no registry
  concept, no staleness tracking, no cleanup.

### Custom home

- **Otter** — first-class: the custom path becomes the container's
  real `/home/<user>`, `HOME` is set correctly, and the host home
  stays reachable at `/run/host/home/<user>`; removal is safe and
  explicit via `otter rm --rm-home` (guards `/`, `/home`, and your
  real home).
- **Distrobox** — `--home` exists but is less uniform: the host home
  stays mounted, path handling varies, and removal is less explicit.

### Supported package managers

- **Otter** — covers everything Distrobox does except apt-rpm/ALT
  Linux and microdnf, and adds more: Nix, Guix, Homebrew, and
  slackpkg (Slackware), among others. Otter keeps its images fresh via
  the registry.
- **Distrobox** — apt, dnf, microdnf, pacman, AUR, slackpkg,zypper,
  apt-rpm/ALT Linux, and more; no image-management layer.

There are no plans to include support for more package managers,
I think the current list is enough & fulfills most needs.
( If you feel need for more, feel free to contribute )

### Settings & delegation

- **Otter** — **TOML** for both the config file
  (`~/.config/otter/otter.conf`) and manifests (`otter assemble`);
  typed settings, `home` field, inheritance between entries; delegates
  the manager (`preferences.container-manager`) and escalation
  (`preferences.sudo-program`) from the same file.
- **Distrobox** — assemble manifests use **INI** syntax; no typed /
  nested config equivalent.

Call me biased but I think **TOML** is infinitely more superior to **INI**

## Otter vs Toolbox

Toolbox is Fedora's official container tool. It's deliberately
minimal; otter is deliberately full-featured.

### Commands available

- **Otter** — a wide surface: `create`, `enter`, `list`, `rm`,
  `start`, `stop`, `restart`, `pause`, `upgrade`, `export`,
  `host-exec`, `assemble`, `registry`, `inspect`, `doctor`, `journal`,
  `service`, `settings`, `redirect`, `generate-entry`,
  `documentation`.
- **Toolbox** — a minimal set: `toolbox create`, `enter`, `list`,
  `rm`, `run`, `stop`, `init-container`, `rmi`, `help`.

### Usecase

- **Otter** — a "second userspace": mix any distro, keep per-project
  isolated state, export apps to the host, run scripts, and manage
  many boxes declaratively.
- **Toolbox** — a disposable, distro-mirroring dev shell on Fedora
  atomic desktops: break it, rebuild it, never touch the host.

### Scope

- **Otter** — a superset: custom home, rootful, `--unshare-*`,
  declarative setup, image registry, exported launchers,
  diagnostics.
- **Toolbox** — mirrors the host Fedora release, shares home and
  services, and stops there: no custom home, no rootful, no
  isolation, no declarative setup, no registry, no app export.

### Other differences

- **Distro choice** — otter runs many images; Toolbox is Fedora only.
- **App export** — `otter export` puts GUI apps and launcher entries
  on the host; Toolbox has no export capability.
- **Rootful** — otter supports `--root`; Toolbox has no rootful mode.
