# Custom Image Build Cookbook

This is the "recipes" companion to `Using Custom Images`, which
covers the *mechanics* of using your own images. Here you'll find
patterns for authoring Containerfiles that otter is happy to run,
modeled on the official images the project builds (in the repo's
`images/` directory).

## Official-derived vs upstream-derived

Your `FROM` line decides the whole support story.

### FROM an official otter image (recommended)

```dockerfile
FROM ghcr.io/ferret-linux/ubuntu-otr:stable
```

- You inherit the base image's helpers, shell, host integration, and
  locale setup.
- The official marker is inherited, so `otter-init` does not show its
  non-official-image warning. Your derived image is still your
  responsibility to maintain and test.
- It remains *your* image — **it is not maintained by otter's
  registry**. Nobody rebuilds, updates, or pulls it for you, and
  official-image-only behavior such as staleness tracking doesn't
  apply; tag and rebuild yourself when a new base ships. See
  `Images` and `Registry`.

### FROM an upstream (non-otter) image

```dockerfile
FROM docker.io/library/debian:bookworm
```

- Recognized as **non-official** and **not officially supported**.
- **First `enter`/setup is much longer**: `otter-init` must detect
  the distro and install the basics (shell, sudo, user, host
  integration) that official images already bake in.
- **No registry support** — none of the registry's official-image
  behavior applies to your base.
- **Features can be limited or error** — host integration, GPU,
  init systems, and helpers assume the official layout; a bare
  upstream base often diverges in paths or missing pieces.
- **Compatibility can need additional fixes** — exotic package
  names, absent users/groups, or nonstandard init may force manual
  patches in your Containerfile.
- Otter is **only tested against official images**; everything the
  tool does with an upstream base is "works in practice", not
  guaranteed.

Deriving from an image in Otter's catalog means less setup work. Use
an upstream base when you need a base the catalog does not provide.
See `Images` for the current catalog.

## Baseline: what otter expects in an image

Otter boots any OCI image, but first-boot init has to *detect*
the distro and install basics, which is slow. An "otter-friendly"
image pre-bakes everything so first enter has nothing to do:

- a supported shell — `bash`, `zsh`, `fish`, or `nu`;
- `sudo` and a container user (e.g. `useradd -m -s /bin/bash`);
- `curl` (official images also add `host-spawn` and `gum`, small
  static binaries otter uses for host integration);
- sane locale/timezone;
- otter's helper layout at `/usr/lib/otter/`, including
  `container.<distro>` marker files.

Deriving from an official otter image inherits all of that. See
`Images` for the base names (`ghcr.io/ferret-linux/<distro>-otr`) and
`Using Custom Images` for which `--image` strings count as "full
references".

## Recipe 1: minimal Debian/Ubuntu box

This one deliberately starts from an upstream base to show the
non-official case. Setup work on first entry depends on the base image
and what it already contains.

```dockerfile
FROM docker.io/library/debian:bookworm

RUN apt-get update && apt-get install -y --no-install-suggests \
        bash-completion curl git sudo vim zsh \
    && rm -rf /var/lib/apt/lists/*

RUN apt-get update && apt-get upgrade -y \
    && rm -rf /var/lib/apt/lists/*
```

```sh
podman build -t my-base:latest .
otter create --image my-base:latest dev
```

`otter-init` provisions the rest (locale, profile, host
integration) on first enter — budget a slower first boot.

## Recipe 2: bake a project toolchain

Baking eliminates per-container first-boot setup and
`--additional-packages` calls. A Node/Python example:

```dockerfile
FROM ghcr.io/ferret-linux/ubuntu-otr:stable

RUN apt-get update && apt-get install -y --no-install-suggests \
        nodejs npm python3 python3-pip \
    && rm -rf /var/lib/apt/lists/*

RUN npm install -g yarn pnpm
```

```sh
podman build -t my-toolchain:latest .
otter create --image my-toolchain:latest web
```

Bake what must be *identical* across boxes (build tools, pinned
tooling). Everything else can stay per-container via
`--additional-packages` — that keeps rebuilds for one project from
touching others.

## Recipe 3: layer hygiene (cache the expensive step)

Each `RUN` is a layer; order cheap first, expensive last so the
cache actually helps. Keep each install in one layer so cleaning is
atomic:

```dockerfile
FROM ghcr.io/ferret-linux/fedora-otr:stable

# Frequently changed bits (shared layers come first)
COPY tooling-requirements.txt /tmp/

# Expensive, pinned step
RUN dnf install -y $(xargs < /tmp/tooling-requirements.txt) \
    && dnf clean all && rm -f /tmp/tooling-requirements.txt
```

Clean package metadata *inside the same layer* (`rm -rf /var/lib/
apt/lists/*`, `dnf clean all`) or every later cached layer carries
dead weight.

## Recipe 4: derive-and-extend

This is the officially supported path from the section at the top:
the official images already carry shell, sudo, host-spawn, gum,
and the `/usr/lib/otter` layout, so deriving is the fastest way to
a *good* image — and it stays recognized as official.

```dockerfile
FROM ghcr.io/ferret-linux/debian-otr:stable

RUN apt-get update && apt-get install -y --no-install-suggests ffmpeg \
    && rm -rf /var/lib/apt/lists/*
```

Your image inherits the base image's helper files and official marker.
It is still your responsibility to rebuild, test, and maintain it.

## Building & iterating

```sh
podman build --pull -t my-recipe:latest .
otter create --image my-recipe:latest test && otter enter test
# then, on changes: rebuild, remove, recreate
otter remove test && podman build ... && otter create ...
```

Build with your container manager directly (`podman build`, `docker
build`, `nerdctl build`); otter consumes the result. For
multi-architecture images, pass `--platform` at build and to
`otter create`. See `Cross-Architecture Containers`.
