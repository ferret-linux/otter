# Using KVM & Libvirt in Containers

If you're on an immutable distribution (Silverblue, Aeon, Vanilla OS,
and similar), installing the whole libvirt/QEMU/KVM stack on the base
system isn't advisable — your system state is managed, and packages
won't survive updates. An otter container is a clean place to run
`libvirt` + `qemu` + `virt-manager` instead, keeping the virtualization
stack fully inside the container.

## Requirements

- A **rootful** container (`--root`) — KVM needs real kernel-level
  access that a rootless container can't provide.
- An **init system** (`--init`) — libvirt runs as a set of services
  (virtqemud, virtnetworkd, virtstoraged, virtnodedevd) that need an
  init system to manage.
- A separate network namespace (`--unshare-netns`) for publishing the
  SSH port below. Keep device access enabled so the container can use
  `/dev/kvm` when the host and runtime permit it.

## Creating the container

```sh
otter create --root --init --unshare-netns \
  --image opensuse-leap \
  --additional-packages "openssh-server patterns-server-kvm_server patterns-server-kvm_tools qemu qemu-linux-user virt-manager" \
  --additional-flags "-p 2222:22" \
  --init-hooks "systemctl enable sshd.service && systemctl enable virtqemud.socket virtnetworkd.socket virtstoraged.socket virtnodedevd.socket && usermod -aG libvirt \$USER" \
  libvirtd
```

What each piece does:

- **`--root`** — rootful container with real root privileges.
- **`--init`** — systemd inside the container to run libvirt's
  services.
- **`--unshare-netns`** — gives the container a separate network
  namespace so the manager can publish port 2222.
- **`--additional-packages`** — the libvirt/QEMU stack, sshd, and
  virt-manager. OpenSUSE images already ship systemd, so no extra
  systemd package is needed.
- **`--additional-flags "-p 2222:22"`** — forwards host port 2222 to
  the container's sshd, so virt-manager can connect over SSH.
- **`--init-hooks`** — enables the libvirt socket units and sshd on
  first boot, and adds your user to the `libvirt` group.

After creation, enter the container (as root, since it's rootful):

```sh
otter enter libvirtd --root
```

## Export virt-manager

From inside the container, export virt-manager to the host so it
appears as a normal host app:

```sh
otter export --app virt-manager
```

Now the **virt-manager** entry appears in your host's application
menu, labeled with its container name — select it, enter your root
password, and you're done. It runs inside the container but launches
from the host like any other app.

## Connecting via SSH

Alternatively, you can connect to the container from an existing,
already-installed virt-manager on the host.

Open virt-manager, then **Add a connection…** and set it up like
this:

- Tick **"Use SSH"**.
- Username: `<your-user-name>` (same user as in the container).
- Hostname: `127.0.0.1:2222` (the forwarded port).

Optionally enable autoconnection. Double-click the connection to
activate it. Configure an SSH key or a password for the container
user; the host account password is not automatically available inside
the container.

## Using a manifest instead

If you prefer a declarative setup (or want to reproduce this on
multiple machines), otter's manifests cover the same thing.
`otter.toml`:

```toml
[[container]]
name    = "libvirtd"
image   = "opensuse-leap"
start-now = true

[container.settings]
rootful     = true
init-system = true

[container.isolation]
netns = true

[container.additional]
packages = ["openssh-server", "patterns-server-kvm_server", "patterns-server-kvm_tools", "qemu", "qemu-linux-user", "virt-manager"]
flags    = ["-p 2222:22"]

[container.hooks]
post-init = [
  "systemctl enable sshd.service",
  "systemctl enable virtqemud.socket virtnetworkd.socket virtstoraged.socket virtnodedevd.socket",
  "usermod -aG libvirt $USER",
]

[container.exported]
apps = ["virt-manager"]
```

Then provision everything with:

```sh
otter assemble create --file otter.toml
```

## Notes

- Do not use `--unshare-all` when you need hardware KVM acceleration:
  it unshares devices and hides the host's `/dev/kvm`. Without KVM
  access, QEMU may fall back to software emulation.
- Official otter images already ship systemd where the distro supports
  it, so `--init` usually needs no extra systemd package — but on
  some images you may need to add it via `--additional-packages`.
- The container must be rootful; a rootless container won't be able to
  use `/dev/kvm` reliably.
