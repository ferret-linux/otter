# Backing Up, Cloning & Restoring

Otter containers are cheap to recreate, but the work *inside* them
(packages you installed, configs you wrote) is what you want to
protect. Because your home directory is the same on host and in
container, your user data is already on the host and backs up like
normal files — what "backing up a container" means here is
preserving the container's **installed state**. This tutorial
covers three complementary ways to do that.

## 1. Clone a container (`otter create --clone`)

The quickest way to duplicate an existing container — for renaming,
or for branching several copies of one environment — is cloning:

```sh
otter stop my-box
otter create --clone my-box my-box-copy
```

The source container must be stopped. otter commits it to a dated
image tag (`<name>:<YYYY-MM-DD>`, e.g. `my-box:2026-09-02`) and
creates the new container from that image. Resulting clone images
are just local container-manager images — otter's registry doesn't
track them. The manifest equivalent is the `clone` field on a
`[[container]]` entry. See `Declarative Manifests & Assemble`.

### What a clone keeps — and what it doesn't

A clone snapshots the container's **static internals**: the
committed filesystem state — installed packages, config files,
and everything else that lives in the container's own filesystem
(layer). It does **not** carry otter-side configuration or
host-side artifacts over from the source:

- **Exported apps & binaries** — `otter export` writes
  `.desktop` files and launcher wrappers on the *host*, keyed to
  the source container's name. Those are not part of the image; a
  clone doesn't re-export them. Run `otter export` again for the
  new name. See `Exporting Apps & Binaries`.
- **Init hooks** — `--init-hooks` / `--pre-init-hooks` run at
  create time. A clone only runs the hooks you pass on the new
  command line (or none at all).
- **Otter flags & settings** — rootful, `--unshare-*`, `--init`,
  `--gpu`, shell, hostname, and memory/cpu limits are *not* read
  back from the source. The clone gets whatever you pass now, or
  otter's defaults. If you originally created the box with `--init`
  (or anything else), pass it again when cloning. Per-enter
  variables set via `--add-env` are only ever enter-scoped anyway,
  so there's nothing to inherit.
- **Desktop entry** — a fresh entry is generated for the *new*
  name; the source's entry keeps pointing at the source.

Host bind-mounts are shared, not owned, so there's nothing to lose
there either: your home directory is the same on host, source, and
clone — user files never need to be part of a snapshot.

If the flags/hooks matter and you don't want to re-type them, bake
them into a TOML manifest (Section 3) where `clone` coexists with
`settings` and `additional` on the same `[[container]]` entry.

## 2. Archive to an image and restore

Clone covers otter-to-otter. To take a container *off* the machine
or turn it into a permanent artifact, commit it to an image and
save that:

```sh
# snapshot the container into an image
otter stop my-box
podman commit my-box my-box-backup:latest

# save the image to a tar archive for transfer
podman save -o my-box-backup.tar my-box-backup:latest
```

(Docker users: `docker commit` and `docker save` — same flow.)

On the target machine, load and recreate:

```sh
podman load -i my-box-backup.tar
otter create --image my-box-backup:latest my-box
```

This is also exactly the migration path from distrobox and Toolbx
containers — see `Migrating from distrobox` and
`Migrating from Toolbx`.

## 3. Declarative manifest (the real "restore")

For a container you care about recreating from scratch, the most
robust backup is the *definition*, not the snapshot. Declare the
container in a TOML manifest and re-create it anywhere with one
command:

```toml
[[container]]
name        = "dev"
image       = "fedora"
start-now   = true

[additional]
packages = ["git", "vim", "nodejs"]

[settings]
init-system = true
```

```sh
otter assemble create --file dev.toml
```

A manifest never goes stale the way a snapshot does, and it's
reviewable in git. Described fully in
`Declarative Manifests & Assemble`.

## Related maintenance

- `otter upgrade` refreshes the *packages inside* an existing
  container (its native package manager). It doesn't move you to a
  newer official base image — that happens at `otter create` time
  (see the staleness/autopull behavior in `otter create`).
- Old dated clone/commit images accumulate; clean them up with
  `podman rmi`/`docker rmi` (they're not registry-managed).
- `otter lock` protects a container from being removed/upgraded
  while you're mid-backup — see `otter lock`.

## Which to use

| Goal                                | Tool                     |
| ----------------------------------- | ------------------------ |
| Rename / branch an environment      | `otter create --clone`   |
| Move a container to another machine | commit → save → load     |
| Reproduce a known-good environment  | TOML manifest + assemble |
| Keep packages fresh                 | `otter upgrade`          |
