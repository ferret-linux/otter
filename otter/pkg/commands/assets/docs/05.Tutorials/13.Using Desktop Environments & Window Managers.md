# Desktop Environments & Window Managers

A container manager isn't just for CLI tooling — the same
host-integration primitives that make `otter enter` feel like a real
shell also make it possible to run a full desktop environment or
window manager from inside a container, launched straight from your
login manager. This is useful if your host tracks a stable-release
distro (Debian, an LTS Ubuntu, a RHEL family member) but you want to
run a much newer GNOME, KDE Plasma, or a standalone compositor like
Hyprland without giving up your host's stability.

**Experimental:** running a full desktop session from a container is
not guaranteed to work with every distribution or desktop release.
Package names, session startup, and compositor requirements come from
the distribution and desktop environment. Use this guide as a starting
point, and check their documentation if a session fails to start.

## Host integration available by default

Otter shares `/tmp`, `/dev`, and `/sys` with the host by default, so
display sockets and devices are usually available without adding
individual mounts. `--unshare-devsys` changes device access. With
`--init`, official images use their detected init system; on images
using systemd, Otter also makes supported host session sockets
available inside the container. See `Host Resource Sharing` for what
is shared and `Initful vs Initless` for the tradeoffs of `--init`.

## Using a stable host with a newer desktop

One approach is to run a newer distribution in the container to get a
newer GNOME or Plasma while keeping the host on its current release.

### Setting up the container

```sh
otter create --init --image fedora-rawhide gnome-de
```

`fedora-rawhide` is a short name in Otter's image catalog. The official
image includes the init system needed by `--init`. Short-name mappings
can change with the registry; see `Registry` for how Otter resolves
them. `--init` also unshares the process and group namespaces by
default; see `Initful vs Initless` for the effect on process visibility.

Enter it once to let setup finish:

```sh
otter enter gnome-de
```

## Running Latest GNOME

Install the desktop group from inside the container, same as on a
native Fedora install:

```sh
[gnome-de]$ sudo dnf group install gnome-desktop
```

(Fedora's group names do shift between releases — if that exact group
id doesn't resolve, `dnf group list` inside the container will show
the current one.)

### Generate a session file

Because `/tmp/.X11-unix` ownership already matches the host (see
above), the only thing left is a session file on the **host's** side
so your login manager (GDM, SDDM, etc.) can find it. Create:

`/usr/local/share/wayland-sessions/otter-gnome.desktop`
(or `/usr/share/xsessions/otter-gnome.desktop` if your login manager
doesn't pick up the former):

```ini
[Desktop Entry]
Name=GNOME on Wayland (gnome-de otter container)
Comment=This session logs you into GNOME, running inside an otter container
Exec=otter enter gnome-de -- gnome-session
Type=Application
DesktopNames=GNOME
X-GDM-SessionRegisters=true
```

Do not pass `-T` here: that option detaches the command. Without it,
`otter enter` runs the session command in the foreground and returns
when the session ends. Ensure `otter` is on the login manager's `PATH`,
or replace it with the absolute path from `command -v otter`.

Note this desktop entry doesn't name the container explicitly, so
this example names `gnome-de` explicitly. Use the name of your
container in the session command.

Log out, and the new session should show up on your login screen.

## Running Latest Plasma

Same container, same pattern — install the Plasma group:

```sh
[gnome-de]$ sudo dnf groupinstall KDE
```

### Generate a session file

`/usr/local/share/wayland-sessions/otter-plasma.desktop`
(or the `xsessions` equivalent):

```ini
[Desktop Entry]
Exec=otter enter gnome-de -- /usr/libexec/plasma-dbus-run-session-if-needed /usr/bin/startplasma-wayland
DesktopNames=KDE
Name=Plasma on Wayland (gnome-de otter container)
```

### If Plasma does not start `kactivitymanagerd`

Some Plasma setups may need this helper started with the session. If
it is installed at `/usr/libexec/kactivitymanagerd`, add this to the
container user's `~/.profile`:

```sh
if [ -f /usr/libexec/kactivitymanagerd ]; then
  /usr/libexec/kactivitymanagerd & disown
fi
```

## Running Latest Hyprland

Hyprland is standalone rather than a full DE, so it gets its own
container rather than reusing `gnome-de`. Since `/dev` is already
shared by default, the only extra thing this container needs beyond
otter's defaults is the D-Bus **system** bus socket (session-bus and
Wayland/Pipewire sockets are handled by `--init`'s socket integration,
same as above — the *system* bus is a separate, always-on socket that
integration doesn't touch):

```sh
otter create --init --image arch hyprbox \
  --volume /run/dbus/system_bus_socket:/run/dbus/system_bus_socket
```

`--volume` adds a mount directly through `otter create`; you do not
need to pass it through `--additional-flags`.

Install Hyprland inside it:

```sh
otter enter hyprbox
[hyprbox]$ sudo pacman -Sy hyprland
```

Then, either run it directly:

```sh
otter enter hyprbox -- Hyprland
```

or, to launch it from a login manager, use the same session-file
pattern as GNOME/Plasma above with
`Exec=otter enter hyprbox -- Hyprland`.

As with the original guide, this requires no other Wayland session to
already be running on that seat. If you want Hyprland running
alongside an existing host session (e.g. on a second tty), give it a
runtime dir and Wayland display name that don't collide with the
host's, using otter enter's
`--add-env`:

```sh
otter enter hyprbox --add-env XDG_RUNTIME_DIR=/run/user/1000/hypr \
                     --add-env WAYLAND_DISPLAY=wayland-hypr \
                     -T -- Hyprland
```

Otherwise, apps launched from inside the container will attach to
whichever Wayland display they find first, which is rarely what you
want if two compositors are alive at once.

## Using apps from the host while inside a DE session

Once you're inside one of these container-based sessions, you'll
likely still want to launch things that live on the host rather than
in the container (a host-only app, checking on the host's own
containers, opening a link in the host's default browser). That's what
`otter host-exec` is for — run from
inside the container:

```sh
[gnome-de]$ otter host-exec firefox
```

The `xdg-open`/`flatpak` symlinks otter sets up inside every container
already route through this mechanism automatically, so "open with" and
similar system integrations mostly work without you needing to reach
for `host-exec` directly. See
`otter export` if you'd
rather go the other direction — making a container app show up as a
normal entry in the host's own application launcher, via
`otter export`.
