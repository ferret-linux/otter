`otter cleanup` — remove otter-managed leftovers from the host.

## Synopsis

```text
otter cleanup [options]
otter purge   [options]
```

`purge` is a full alias of `cleanup`; both behave identically.

## Description

`cleanup` builds a plan of host-side leftovers that otter can prove it
owns, then acts on that plan. It is a global sweep rather than an
owner-scoped operation like `otter remove`: it looks for stale export
records and files, generated desktop pins, cached icons, temp artifacts,
and container engine images left behind after containers, exports, or
entries are gone.

### What is scanned

- **Export index and records** under
  `~/.local/share/otter/exports/index/<manager>/<rootful|rootless>/<container>/`.
- **Exported files and icons**: otter-marked binaries in the managed
  export directories (including every `--scan-path`) and exported app
  icons under `~/.local/share/otter/icons/apps/`.
- **Export temp and backup artifacts** (`.otter.tmp.*` and
  `.otter.bak.*`) in the managed export directories and the index.
- **Generated desktop pins**: `.desktop` launchers in
  `~/.local/share/applications/` created by `otter generate-entry`.
- **Unused cached icons** under `~/.local/share/otter/icons/distros/`
  and `~/.local/share/otter/icons/apps/` that no remaining pin or
  export record references.
- **Engine images** visible to the configured container managers
  (podman, docker, nerdctl).

### What is never touched

- Files, desktop entries, or icons without valid new-style otter
  ownership markers.
- Unmarked legacy pins (the old `<container>.desktop` and
  `rootful-<container>.desktop` filenames) and any item whose provenance
  cannot be verified: these are reported, never deleted.
- Images still in use by an existing container, and images outside the
  selected managers.
- Container storage, custom home directories, and anything inside a
  running container. `cleanup` is a host-side sweep only.

### Rules

1. Only an item whose ownership markers still match its record is
   eligible for deletion. Records whose file is gone or whose markers
   changed are stale and are dropped from the index.
2. By default the plan is **applied**: eligible leftovers are deleted.
   Anything that is only reported stays on disk.
3. Scope follows `settings.rootful` and the configured manager(s).
   `--root` overrides the root mode for this invocation (explicit
   `--root=false` opts out), and `--all-managers` adds every installed
   podman/docker/nerdctl manager to the scan.
4. Engine images are **not scanned** by default: no image is inspected,
   reported, or deleted unless `--images` is passed. With `--images`,
   image candidates are included in the plan and deleted in apply mode;
   images in use by a container are still skipped. Under `--no-apply`
   they remain plan-only.
5. Extra roots given with `--scan-path` are treated as additional
   export candidate roots. They are scanned for otter-marked exports
   only; unrelated files there are ignored.
6. A hard failure, a conflict between two claimed owners, or an item
   with unverified provenance makes the exit status nonzero. Benign
   skips — a path that is already absent, a directory that is already
   clean, or an item that simply is not otter-owned — keep it zero.

## Default behavior

By default `cleanup` acts: it applies the plan and deletes eligible
leftovers, then reports what was removed and what was only reported.
**Deletion is final — there is no quarantine area and no restore
command.** Recreate anything you still need using the steps in
[Recovery](#recovery).

`--no-apply` prints the plan instead. In plan-only mode otter does not
write files, does not take the global export lock, and does not
escalate privileges through `settings.sudo-program`. It is safe for
inspection and for use in scripts that only want a report.

## Options

| Flag                 | Alias  | Description                                           |
| -------------------- | ------ | ----------------------------------------------------- |
| `--no-apply`         |        | Plan only; no writes, no locks, no escalation         |
| `--json`             |        | Machine-readable plan/report                          |
| `--root`             | `-r`   | From `settings.rootful`; `--root=false` opts out      |
| `--all-managers`     |        | Include installed podman/docker/nerdctl managers      |
| `--images`           |        | Allow final image deletion (default: report only)     |
| `--scan-path <path>` |        | Additional export candidate root (repeatable)         |

## Options Explained

### `--no-apply`

Plan only. The same candidates are discovered and reported, but nothing
is written: no files are removed, no lock is taken, and no privilege
escalation is attempted. Combine with `--json` for a scriptable report.

### `--json`

Emit the plan (with `--no-apply`) or the completion report as JSON
instead of human-readable text. Useful for scripts and external apps.

### `--root`, `-r`

Select the root mode from `settings.rootful`, the same default used by
other host commands. Pass `--root=false` to explicitly opt out and stay
rootless for this invocation.

### `--all-managers`

By default only the container manager(s) configured for this user are
scanned. `--all-managers` also scans every installed podman, docker,
and nerdctl manager, so leftovers from a runtime you no longer use are
included in the plan.

### `--images`

Enable scanning and the final deletion of engine images identified as
otter leftovers. Without this flag images are not scanned at all; under
`--no-apply` they stay plan-only even with this flag. Images currently
used by a container are skipped either way.

### `--scan-path <path>`

Add a file or directory to scan for otter-marked export candidates, in
addition to the default export directories. Repeat the flag for
multiple roots, as with `otter exports rebuild`.

## Examples

```sh
otter cleanup
```

Plans and applies cleanup for the configured managers and root mode.
Images are not scanned.

```sh
otter cleanup --no-apply
```

Shows what would be removed without writing anything or taking a lock.

```sh
otter cleanup --no-apply --json
```

Same inspection, with a machine-readable report.

```sh
otter purge --root --all-managers
```

Applies cleanup across every installed manager, in root mode.

```sh
otter cleanup --images
```

As the default run, but also deletes leftover engine images.

```sh
otter cleanup --scan-path /srv/exports --scan-path /mnt/share/bin
```

Also considers those two roots when looking for otter-marked exports.

## Exit Codes

- `0` — the plan or report completed; anything skipped was skipped for
  a benign reason (already gone, already clean, not otter-owned, or an
  image left in report-only mode).
- Nonzero — a hard failure (for example an engine that cannot be
  queried, or a deletion that fails), a conflict between owners, or an
  item whose provenance could not be verified. Such items are reported
  and never deleted.

## Recovery

Deletion is final: items removed by `cleanup` are not quarantined and
cannot be restored by otter. Recreate what you need explicitly:

- Desktop pins: `otter pin <name>` (or
  `otter generate-entry <name>`) regenerates a launcher; `--all`
  regenerates them for every container.
- Export index: if records were dropped but the exported files still
  carry otter ownership markers, `otter exports rebuild` rebuilds the
  index from those markers. If the exported file itself was removed,
  re-export the app or binary from its container.
- Images: pull them again with `otter registry pull <short-name>`, or
  run `otter create` and let its normal staleness-aware pull restore
  the image. Local or non-otter images must be re-pulled with the
  container engine's own CLI.

## Notes

- `cleanup` is deliberately conservative: marked leftovers are deleted,
  unmarked legacy pins and unknown items are only reported. Being
  reported does not mean an item was removed.
- With `--no-apply` the run is read-only with respect to the host
  integration state, so repeated planning runs are safe.
- Deleting an export record without deleting its file is recoverable
  via `otter exports rebuild`; deleting the file is not.
