# Registry

Otter doesn't ship its catalog of official images inside the `otter`
binary itself. Instead, it keeps a live manifest describing every
image it knows how to offer — one entry per short name — and consults
that manifest whenever it needs to resolve a name, check whether an
image is current, or list what's available. This page explains how
that system works. For how the images themselves are actually built,
see `Images`.

## The manifest json

The registry's source of truth is a single JSON file, fetched from
the upstream Otter project rather than stored on disk between runs.
Each time otter needs it — listing the catalog, resolving a short name,
checking staleness — it fetches a fresh copy over the network rather
than reading a local cache. This means the catalog you see is always
current with upstream. These operations therefore need network
access; if the fetch fails, Otter cannot resolve short names or show
the live catalog. Full image references bypass the registry.

Each entry in the manifest describes one image: its short name, the
image it resolves to, which architectures it's available for, whether
it's currently enabled, and build/versioning info used for staleness
tracking (see below).

## Referring to images by short name

Anywhere otter accepts an image (`otter create --image`, manifest
`image` fields, `otter registry pull/remove`), a short name is checked
against this catalog and resolved (case-insensitively) to an actual
image reference. Anything containing `/` or `:` is treated as a full
image reference instead, and is used exactly as given — bypassing the
registry entirely. See `Images` for the
list of built-in short names.

## Enabled vs. disabled entries

Each registry entry can be independently enabled or disabled
upstream. A disabled entry still resolves by short name, but to its
**fallback vendor image** — the distro's plain official image —
rather than otter's optimized build, so a short name always resolves
to *something* even if otter's own build for it is temporarily pulled.
`otter registry list` hides disabled entries by default; pass `--all`
to see them along with their status.

If an entry is removed from the manifest, its short name is unknown
and cannot be resolved.

## Staleness tracking

Every otter-built image bakes in a build number at build time. When
you already have an image pulled locally, otter compares your local
build number against the latest one recorded in the manifest to
decide how fresh your copy is:

- **Current** — your local build matches the latest known remote
  build; nothing happens.
- **Behind** — the remote build is ahead of yours. Depending on how
  far behind you are, otter either just warns you or pulls the newer
  image automatically — both thresholds are configurable (see
  `Configuration`).
- **Ahead** — your local build is somehow newer than the latest known
  remote build; not expected in normal use but can happen (safe to ignore).
  In this case otter just warns instead of pulling and refreshing the image.
- **Unknown** — the local image is missing its build info entirely
  (e.g. an older image, or one pulled before this tracking existed);
  otter treats it like a missing image and pulls to heal it.

This check runs both when you create a container from an existing
local image, and when you run `otter registry list`.

## Where this runs

The registry isn't a separate step you have to remember to run — it's
consulted automatically wherever otter needs to know about an image:
browsing, pulling, or removing images directly with
`otter registry`, and resolving or
freshness-checking an image as part of
`otter create`. Both paths go through the same
manifest json and the same staleness logic; there's no separate tracking
state kept per-command.

## Automatic cleanup of replaced images

When a pull brings in a newer build of an image you already had
locally — for example, a stale image getting auto-pulled, or a manual
`otter registry pull` refreshing one — the old build left behind
isn't kept around. Otter removes it automatically afterward, as long
as no otter container is still using it; if one is, the old image is
left in place until nothing depends on it. This runs the same way
whether the pull was triggered manually or automatically, so old
builds don't quietly accumulate on disk over time.
