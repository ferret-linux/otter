# Custom Home

By default, Otter bind-mounts your host home for use as the
container user's home. On hosts whose home directory is `/var/home`,
Otter maps it to `/home/<user>` inside the container. This is the
source of Otter's close host integration, but it
also means that tools writing to `~/.config`, `~/.cache`, or
`~/.local` can pollute your host home or collide with other
containers. The `--home` flag gives you a clean, isolated home per
container without giving up the integration that makes otter useful.

## How otter does it

When you pass `--home /some/host/path` to `otter create`, otter
bind-mounts that path as the container's home and sets
`HOME=/home/<user>` inside the container. Tools that use `$HOME`
write to the custom directory instead of the regular host home.

The host path is created automatically if it doesn't exist yet.

Inside the container, `$HOME` always resolves to `/home/<user>`,
regardless of the host distribution. This is uniform whether you
run rpm-ostree/bootc, NixOS, Arch, Fedora, or anything else — the
container always sees a conventional Linux home path. This keeps
apps that hardcode `/home/<user>` (many Electron apps, for
instance) working correctly.

## What stays shared

Otter's host integration depends on several bind mounts that
cannot be removed: the host filesystem at `/run/host`, the X11
and Wayland sockets in `/tmp`, the runtime directory, and device
nodes under `/dev`. These are hard requirements — many of otter's
commands and integrations (host-exec, desktop entry generation,
GPU passthrough, journal forwarding) rely on them. Custom home
isolates your dotfiles and configs; it does not create a
filesystem sandbox.

In practice, your regular host home remains reachable through
`/run/host` even with `--home`. Programs can still read or write host
files there if you direct them to those paths; custom home only
changes the home directory applications see through `$HOME`.

## When to use it

- **Per-project isolation** — separate `node_modules`, Python
  venvs, Cargo registries, and editor configs between containers
  so they don't conflict.
- **Multiple containers, different distros** — two containers
  sharing the same home can fight over dotfiles (e.g. two
  versions of the same KDE config). Custom home prevents this.
- **Clean host home** — if you want to experiment in a container
  without leaving debris in `~/.cache` or `~/.local`.

Custom home is not needed when you want full host integration
(the default) — most users run with the default shared home and
only reach for `--home` when they hit a specific conflict.
