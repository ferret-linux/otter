# Compatibility

## Host architecture

Official Otter images are published for **amd64** and **arm64**. An
individual image may support only one; check `Images` before using it.
Third-party images may support other architectures, but those are
outside Otter's supported image set.

## Container managers

Otter works with **Podman**, **Docker**, and **nerdctl**. One of the
three must be installed and working; otter auto-detects whichever is
available, or you can select one explicitly via
`preferences.container-manager` in `otter.conf` (see `Configuration`).

Podman gives the most out-of-the-box experience for rootless use. If
you use rootless Docker, configure its rootless mode yourself — Otter
does not set it up. Rootless nerdctl is not currently supported by
Otter; use rootful nerdctl or choose Podman or Docker for rootless use.

## Privilege escalation

For anything that needs root (`--root`), otter supports `sudo`,
`sudo-rs`, `doas`, `run0`, and `pkexec`. By default it autodetects one,
trying them in that order; you can pin a specific program via
`preferences.sudo-program` in `otter.conf`.

You are not supposed to use `sudo otter` or similar by convention;
`otter --root` is the official and only-supported way to use rootful
container management on otter.

## Init systems

Inside containers created with `--init`, **systemd** gets the most
testing. **OpenRC**, **dinit**, **sysvinit**, and **runit** are also
supported directly. Other init systems are handled through generic
`/sbin/init` support, without the init-specific integration the five
above get.

## GPU support

Otter has official, first-party support for the NVIDIA Container
Toolkit, detected automatically when it's set up on the host.

AMD and Intel GPUs don't need special handling, as they are already
handled by the kernel (on the host) and mesa packages (inside the
container). NVIDIA is a special case due to out-of-tree kernel
modules and drivers.

## Host kernel and storage

Otter delegates container creation and storage to your container
manager. The kernel features and storage drivers required therefore
depend on that manager and your configuration; Otter does not require
OverlayFS specifically. Cgroup v2 is required for the live systemd
resource-control examples in `Applying Resource Limits`. Check your
manager's installation and system requirements if it cannot start a
container.

## Image support tiers

Otter's built-in registry images are curated and otter-optimized —
see `Images`. Any other image (a full image reference, your own custom build,
or a distro not in the built-in catalog) will work,
but isn't held to the same standard: package sets, setup steps, and
host integrations may be incomplete or behave differently. Custom and
third-party images may need extra setup before all Otter features work.

## Keeping software current

Otter does not enforce minimum versions for container managers or OCI
runtimes. Keep them updated through your distribution and check their
current installation requirements if you encounter compatibility
issues. See the official [Podman installation guide](https://podman.io/docs/installation),
[Docker Engine installation guide](https://docs.docker.com/engine/install/),
and [nerdctl releases](https://github.com/containerd/nerdctl/releases).

## Host integration

Flatpak is not required to use Otter. The in-container commands
`otter host-exec` and `otter redirect` may require the Flatpak D-Bus
service to be available on the host. If you do not use those commands,
you do not need this integration.
