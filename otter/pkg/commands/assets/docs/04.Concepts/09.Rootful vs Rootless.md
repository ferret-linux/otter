# Rootful vs Rootless

Otter runs containers **rootless by default** and only escalates
when you explicitly ask. Whether a container is rootful or rootless
changes who owns its files, which stores it lives in, and — for
some workloads — whether it can work at all.

## Rootless (default)

The container manager runs as your user. It maps container users and
files to your host user account; the exact mapping depends on the
manager. Consequences:

- Container processes and files are owned by your uid, and your
  uid inside maps to your host uid via the user namespace, so
  `ls -l` shows *your* user.
- With Podman, rootless containers use a per-user store rather than the
  system-wide store. Other managers use their own storage locations.
- No password prompt required to create, enter, or manage
  anything.

Rootless is the right choice for most development and interactive use.
Podman supports this mode directly. Rootless Docker needs to be set up
separately, and Otter does not currently support rootless nerdctl.

## Docker & nerdctl: rootful daemons by default

Docker and nerdctl commonly use a daemon, so the CLI may need access
to a daemon socket. With a standard rootful daemon, that access is
usually granted through an administrator-controlled group or by using
`--root`. Docker also has a separately configured rootless mode; Otter
does not configure it for you. Otter does not currently support
rootless nerdctl. See `Compatibility` for the supported manager modes.

### Permission to reach the daemon

Because the daemon socket is root-owned, access on a normal install
comes from membership in the **docker group** (or whichever group
owns the socket). If your host user isn't in that group, every
otter command fails with a permission error. In that case `--root`
isn't a convenience — it's **required**, because otter escalates the
CLI invocation so it can reach the root-owned socket:

```sh
otter create --image fedora hq-box    # fails: can't reach daemon
otter create --image fedora hq-box --root
```

The same applies to nerdctl and its containerd socket. Note that
being in the docker group is roughly equivalent to root on this
setup, so that group is normally restricted — which is exactly why
a manually configured rootless Docker setup is the way to run it
without using the root-owned daemon socket.

## Rootful (`--root`)

`--root` re-runs the container manager through a privilege-
escalation program, so everything happens as root. Consequences:

- The container and its files are owned by root.
- Rootful and rootless containers live in different stores and
  are managed separately — `otter list` without `--root` won't
  show rootful containers, and `otter enter <box>` needs `--root`
  to enter one.
- A rootful container runs under host root privileges. Because host
  resources are shared by default, use this mode only when your
  workload needs rootful access.

When to use `--root`:

- Services that need to bind privileged ports or touch host
  systems the rootless user namespace blocks.
- System-level virtualization such as libvirt/KVM (see Using KVM &
  Libvirt in Containers).
- Cases where containers need to manage host resources directly.
- Any Docker/nerdctl host whose daemon socket your user can't
  reach (you're not in the docker/nerdctl group). With those
  managers `--root` is the path that works, not a hardening choice.

### The escalation program

`--root` doesn't hard-code sudo. Otter supports `sudo`, `sudo-rs`,
`doas`, `run0`, and `pkexec`, and by default autodetects one in
that order. Pin a specific one with the `preferences.sudo-program`
config value:

```toml
[preferences]
sudo-program = "doas"
```

`--root` on the command line applies to create, enter, list,
start/stop, remove, upgrade, and the other commands that take it.
You should **not** prefix a command with `sudo otter ...`; the
supported way is `otter ... --root`.

## Config as a default

You can default to rootful for new containers via the settings:

```toml
[settings]
rootful = true
```

This is a convenience default only — `--root` explicitly on the
command line overrides any container-creation behavior, and whether
an existing container is rootful is fixed at creation time (recorded
as the `otter.rootful` label, visible via `otter inspect`).

## Choosing

- Prefer **rootless** unless a workload genuinely needs root.
- Don't make containers rootful "just in case" — the rootless
  boundary is the main thing separating an otter container from
  broad host access for your user.
